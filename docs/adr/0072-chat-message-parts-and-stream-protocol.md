# 0072. Chat messages are typed parts, streamed over one typed protocol

- Status: Accepted; amends [0031](0031-read-only-qa-chat.md), [0046](0046-chat-context-mentions.md), [0055](0055-review-folded-into-chat-with-verification.md), [0057](0057-chat-request-queue.md), [0061](0061-review-insights-on-the-diff.md) and [0070](0070-model-port-capabilities-and-a-model-registry.md)
- Date: 2026-10-30

## Context

A chat message was one Markdown `content` string with side lists (`mentions`, `citations`, an error code), and streaming was `chat:delta` (`append`, `reset`, `progress`) beside `chat:message-updated`. The port of ADR 0070 now reports reasoning, tool starts and ends with a short description, and text blocks, but the chat flattened all of it into one status line and dropped the text written before each tool call. A stored answer and a live one had different shapes (the renderer rebuilt a question's chips from `[[@n]]` tokens and kept a separate "progress" field), the renderer's reducer had to special-case each delta kind, and a streaming Markdown renderer (next) needs a text stream per block of text, not one growing string. The chat UI survey (Vercel AI SDK UI, assistant-ui, Deep Chat, TanStack AI) found the same answer everywhere: a message is a list of typed parts, a stream is start/delta/end per part plus message-level status, and a request's lifecycle is explicit. It also recommended keeping the Lit chat (ADR 0003), since what beuve needs (atomic mention chips, validated citation pills, findings with Stage, the main-side queue) is app semantics no library has.

## Decision

- **Parts.** A message is `parts: ChatPart[]` (the chat domain's `chat-message.ts`, `ChatPartView` in the contract), each with an `id` unique in its message (`p1`, `p2`, …, never reused): `text` (Markdown, a plain string), `reasoning` (`running | done`, an optional content-free `summary`), `tool-call` (`tool`, the port's `description`, `running | done | failed | stopped`), `mention` (lines attached to a question, where the question names them; ADR 0046), `finding` (the n-th finding of the message's `review`, ADR 0055, which stays the structured result) and `error` (main's code; the view adds what to do). Citations stay message-level: the validated markers of the text parts. Stored and live messages have the same shape; a question's `[[@n]]` text and its mention list are derived from its parts for prompts (`chatTextFrom`, `chatMentionsFrom`), and a `/review` answer's history text from its findings (`reviewMarkdownFrom`) instead of being stored twice.
- **Statuses.** A request is `queued` (behind the session's running one, ADR 0057), `submitted` (taken from the queue, nothing arrived yet), `streaming` (a part arrived), then `done`, `error` or `cancelled`; every other message is `done`. `chat:cancel` works in every state before the last three and aborts the request's `AbortSignal`, which reaches the model adapter.
- **Main folds the port into parts.** `applyModelEvent` (pure, chat domain) takes the port's `ModelProgress` and `TextStreamEvent` and gives the new parts plus part events: thinking opens a reasoning part (a new summary ends it and opens another), a tool start opens a tool call that its end closes, text opens a text part on its first append and `text-end` closes it, and the port's `reset` discards the text parts written so far (the final answer is the last turn's, as before). `answerPartsFrom` ends a request: what is open is closed (a running tool as `stopped`), the validated answer replaces the streamed text and keeps its part id, a review adds one `finding` part per finding, a failure keeps what streamed and adds an `error` part. An orphaned unfinished answer (the app died) is ended the same way as `cancelled`. The parts are stored at most once a second while streaming, as the preview was.
- **One push channel, `chat:stream`** (replacing `chat:delta` and `chat:message-updated`), carrying `ChatStreamEvent`s keyed by `sessionId`, `messageId` and, for parts, `partId`: `status { submitted | streaming, activity? }` (`activity` is `/review`'s coarse line, never content), `part-start { part }` (a text part always empty), `text-delta { partId, text }`, `part-end { part }`, `part-discard { partId }`, and `message { message, droppedTurns? }`, the stored message, which is authoritative and the only way a request ends. Electron delivers one channel in order, so a text part's deltas between its `part-start` and its `part-end`, `part-discard` or the message's end concatenate to its text; `textPartStream` (renderer) turns them into a WHATWG `ReadableStream<string>` that closes on the part's end and errors on a discard, for the streaming Markdown renderer to pipe.
- **The renderer renders from a reducer.** `reduceChatTranscript` (pure, tested without DOM) folds `chat:list`, `chat:ask` and `chat:stream` into the transcript; events for a message not yet listed wait and are replayed in order when `chat:ask` answers, events for an ended message are ignored, and a reload keeps a request running here. The drawer lays a message out with `planMessageParts`: each run of reasoning and tool calls is one block, open while the request runs and folded into one line ("Thought · 3 tool calls") once it ends; text renders as before (the safe subset, pills only once final). Its transcript buttons go through one delegated click listener that reads `data-action` and `data-*` (chips look their mention up in the transcript by message and part id).
- **Migration** `chat-0002-message-parts` (the chat domain's, ADR 0006) rebuilds `chat_messages` with `parts` in place of `content`, `mentions` and `error_code`, and renames `complete` to `done` and `failed` to `error`. A question is split at its `[[@n]]` tokens into text and mention parts, a `/review` answer gets one finding part per stored finding, a failed one an error part with its code. SQLite can't rewrite JSON lists well in SQL, so `Migration.up` may now be a function run in the migration's transaction (`#sqlite/run-migrations.ts`); the migration keeps its own copy of the conversion so it never changes with the domain's helpers.
- **Also.** Main remembers the installed `claude --version` check of an Agent SDK entry per executable (path, leading arguments, size and modification time; `createClaudeCodeVersionCheck`), so it runs once rather than on every request; a `not-installed` answer is never kept.

## Consequences

- A live answer shows what the model is doing as it does it (thinking, each file read or search), and a stored one keeps that record, folded. Text the model wrote before a tool call still vanishes when the next turn starts, as before; showing it as narration would be a later choice.
- Adding a kind of part is a union member, a migration-free JSON field and a renderer case; the protocol needs no new event.
- The `/review` verification pass reports no progress, so its tool calls don't show as parts; the status line still says it runs. (Changed by [0073](0073-streaming-markdown-renderer.md): it reports them now.)
- Two contract channels went away; anything listening to `chat:delta` or `chat:message-updated` (only beuve's renderer) moved to `chat:stream`. ADR 0061's insights now arrive in `message` events.
- A database migrated forward can't be opened by an older beuve.
