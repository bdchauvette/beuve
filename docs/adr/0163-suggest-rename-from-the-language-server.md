# 0163. Suggest Rename: a language server's rename becomes one note's suggestions

- Status: Accepted; builds on [0162](0162-suggestions-are-a-notes-list-of-replacements.md); amends [0016](0016-in-house-lsp-client-read-only.md) (two more requests)
- Date: 2026-11-27

## Context

"Call this `retryBudget`" is one of the most common review comments, and the most tedious to turn into code: the definition and every use, often across files. Opening an editor on the review-edits branch (ADR 0088) for that is a long detour. beuve already runs the checkout's language servers (ADR 0016, 0111) at the session head, and LSP's rename does not write anything: `textDocument/rename` answers a `WorkspaceEdit`, a list of text edits. With suggestions on any line of any file (ADR 0162), that answer fits a note as it is.

## Decision

- **Command.** Analyze › Suggest Rename… (`suggest-rename`), F2 on both platforms (the VS Code and Zed key), also on the diff line and sheet context menus. It is enabled when the cursor is on a head-side token of a file whose language server advertises `renameProvider` (menu condition `rename-target`). It runs in the main window and in sheets; a sheet hands the result to the main window as `sheet:add-note` does.
- **Requests.** The multiplexer gains `prepareRename` (when the server has `prepareProvider`) and `rename`, both read requests: the client still never sends `didChange` and nothing is written (ADR 0016's rule stands). Client capabilities announce `rename.prepareSupport`. Positions use the negotiated encoding, as hover and definition do. Each request carries its head (ADR 0078), forwards the caller's `AbortSignal`, has a ten-second deadline and is superseded by the next rename.
- **Asking for the name.** A small field at the token, pre-filled with `prepareRename`'s placeholder (or the token), selects it; Return asks for the rename and Escape cancels. A name equal to the old one does nothing. `prepareRename`'s refusal ("cannot rename this element") is shown in place.
- **What is kept from the answer.** `changes` and `documentChanges` text edits are read; resource operations (create, rename, delete a file) are left out and the preview says so. An edit is kept only when its URI resolves, after symlinks, inside beuve's head checkout and names a path tracked in the head's tree (`findTreeBlob`), so install output (`node_modules`, build directories) and files outside the repository never become suggestions; the others are counted in the preview. A server answer is untrusted input: paths are validated as anchors are (ADR 0023).
- **Edits to suggestions.** Main applies each file's text edits to its head blob and splits the result into change regions, merging regions that touch: each region is one suggestion of whole lines. The conversion is pure (`suggestionsFromTextEdits`, in `src/main/lsp`), because it joins the LSP and URA domains.
- **Staging.** A preview lists the files and the number of changes in each, with the left-out counts. Stage creates one note: label `suggestion`, title "Rename `old` to `new`", anchored at the token's line, body empty, its suggestions in path then line order. The note is ordinary from then on: suggestions can be edited or removed one by one, and posting and exports place them by ADR 0162's rules.

## Consequences

A rename across a change is two keystrokes and a name, and the author or agent receives it as concrete edits rather than an instruction. Its quality is the server's: a server that renames text in comments, or misses dynamic uses, produces exactly that. A rename touching lines outside the diff mostly lands in the GitHub review's `<details>` section with permalinks, which is readable but cannot be applied with GitHub's button; agents get all of it. The same pipeline can later take code actions (quick fixes, organize imports), which also answer `WorkspaceEdit`s; that needs its own ADR, because code actions can also run commands on the server.

## Amendment 2026-11-27: as built

- **Channels.** `lsp:rename-support { sessionId, sha?, path }` says whether a server that handles the file advertises `renameProvider`; it starts the server, answers `supported: false` for any commit but the session head, and the renderer asks once per head and file when the reviewer clicks a head-side token. `lsp:prepare-rename` and `lsp:rename` take `expectedHeadSha` (ADR 0078, `perHeadInvokeChannels`) and refuse with `stale-review` when the head moved. Both run in one request scope of kind `rename` per window (ADR 0079), so the next of either supersedes the one in flight; the ten-second deadline (`AbortSignal.any` with `timeoutSignal`) bounds only the server request, and a timeout says so. A sheet may invoke `lsp:rename-support` and `lsp:prepare-rename`; `lsp:rename` is the main window's.
- **The condition.** `rename-target` holds while the diff (or the sheet, at the head) has the focus and its last clicked head-side token is in a file whose server can rename. A right-click doesn't pick a token; the context menus offer the item for the token last clicked.
- **Asking for the name.** Without `prepareProvider`, or when the server answers `defaultBehavior`, the token is the identifier at the column (`[\p{L}\p{N}_$]+`) of the head's line. A server's error answer to `prepareRename` is its refusal, shown in place in one line of at most 300 characters; `null` reads "The language server can't rename this." The old name in the title is that identifier, read from the head; a new name equal to it is refused by main as well as ignored by the field. A new name is one line of at most 200 characters, without control characters or surrounding spaces.
- **Reading the answer.** Client capabilities announce `workspace.workspaceEdit { documentChanges: true, resourceOperations: [] }`, and `documentChanges` is read instead of `changes` when it is an array, as the protocol says. Snippet edits and other shapes are counted as unreadable. A document is kept when its URI resolves (`resolveWorkspaceFile`: lexically inside, then after `realpath`, a regular file) inside the checkout; its real relative path must pass the anchor path rules (`checkUraPath`, now shared with `validateUraItem`) and name a blob of the head's tree. Edits of two URIs that resolve to one file are joined, so a symlinked alias can't add a second, overlapping set unnoticed.
- **Waiting for the server.** tsserver answers a rename while it is still loading its project with only what it has read (an import's local name alone). The multiplexer waits up to five seconds for the server to report on the file, as diagnostics do, before asking. typescript-language-server runs with `providePrefixAndSuffixTextForRename` off, so a rename asked at a use of an imported name renames the declaration and every use rather than introducing `c as double`.
- **Edits to suggestions** (`suggestionsFromTextEdits`). Columns are converted from the server's encoding against the head blob's lines, not the checkout's file. Lines follow LSP (`\r\n`, `\n` and `\r` end one; a column past the end is the end), suggestions follow the model (`\n`-separated, a `\r` stays in its line). Edits with no unchanged line between them form one region, as git's hunks do; each region is trimmed of lines it leaves as they were, and one that leaves a single empty line takes its neighbor along (ADR 0162). A file whose edits overlap, point past the end, end before they start, or add or remove the final newline is left out, named with its reason in the preview; so is a file with a region over 64 KiB.
- **The item limits.** A rename whose suggestions number more than 500 is refused with a message that says how many there are and points to the review edits branch (ADR 0088), rather than split over several notes as the harvest does: a rename is one change, and half of it staged is worse than none.
- **The field.** `beuve-rename-field` is a top-layer popover (`popover="auto"`, so a click outside dismisses it) under the token, or, when there is no token on screen (a rename handed over by a sheet), at the top of the diff, under the window's band; it holds the name field, the refusal or failure, and the preview with Stage and Cancel. Stage sends the previewed suggestions with `ura:create`, which checks them against the head again; nothing else is kept between the preview and staging.
- **From a sheet.** The sheet asks for the name at its token, then hands the request to main on `sheet:add-note` with `rename { character, newName }` (one line only), checked like a note against the sheet that sent it. Main brings the main window forward with `ura:compose`; when it shows that session at that head, it asks for the rename and opens the preview at the top of its window; otherwise it says why, as for a note.
