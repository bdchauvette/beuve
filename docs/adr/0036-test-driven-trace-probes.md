# 0036. Test-driven trace probes: source instrumentation through a Vitest transform

- Status: Accepted
- Date: 2026-10-28

## Context

Pressing `r` on a hunk (spec 5E), or calling `beuve_run_trace_probe` (spec 5C), should run the tests covering the hunk and show an execution timeline: function entry with argument values, which side of each branch was taken, loop iteration counts, and the return value or exception, mapped to head lines. The spec's target is 200 ms. Constraints:

- beuve is authoring-resistant: the probe must never write into the user's checkout, and the head worktree (ADR 0020) must keep holding exactly its commit.
- That worktree has no `node_modules`, so neither Vitest nor the project's dependencies resolve from it.
- Running tests executes the repository's code and config, the same trust problem as language-server binaries (ADR 0017).
- The domain may not import the syntax domain (ADR 0002); it reads trees through its own node interface, like `flow` and `impact` (ADRs 0015, 0028).

### Spike

A two-test TypeScript fixture and one of beuve's own test files (`find-function-at.test.ts`, which loads tree-sitter wasm), on a 4-core Linux container, Vitest 5.0.5, Node 22:

| Run                                                                  | Fixture         | beuve test file |
| -------------------------------------------------------------------- | --------------- | --------------- |
| Cold: one `vitest run` process (5 runs)                              | 550–1130 ms     | 650–780 ms      |
| Cold, through `runTraceProbe` end to end (temp setup, run, parse)    | 680–745 ms      | –               |
| Warm: one `createVitest` instance, `invalidateFile` + rerun one file | 140–190 ms      | 180–195 ms      |
| Warm instance creation / its first run                               | 90–170 / 250 ms | 90 / 320 ms     |
| Planning and applying edits (550-line file, 19 probes, no parse)     | 2.4 ms          |                 |

Most of a cold run is Vite and worker startup, not the test or the instrumentation.

Three ways to observe execution were weighed:

- **(a) Source instrumentation in a Vite transform.** Insert recorder calls into the functions enclosing the hunk before Vite compiles them. Works in every Vitest pool, sees ordering and values, needs no debugger, and costs one string substitution. The transform can be injected by a config beuve generates in its own temp directory.
- **(b) V8 inspector logpoints** (`Debugger.setBreakpointByUrl` with logging conditions). No transform, but Vitest runs tests in worker processes or threads, each needing its own inspector session attached before the module loads; locations must be mapped through Vite's inline source maps; every logpoint is a debugger pause and round trip. Fragile and slow at loop-heavy code.
- **(c) V8 precise coverage.** Cheap and branch-aware, but has no order, no values and no iteration counts per call, so it can't produce a timeline. Useful later for test selection (below).

## Decision

**Approach (a).** `src/internal/trace/` holds the pure planner, the recorder, the reducer and the Vitest runner.

- **Planning.** `planInstrumentation(root, { path, changedLines }, rules)` reads a `TraceSyntaxNode` tree (tree-sitter nodes satisfy it) with a per-language `TraceRules` table (`ecmascriptTraceRules` for TypeScript, TSX and JavaScript; a test checks every type and field against the grammars). It targets the innermost function enclosing each changed line and gives each one an `enter` probe (parameter names; destructured parameters are read from `arguments` where functions have it) and a probe per `if` and ternary condition, `switch` value, `case` and `default`, loop, `catch`, `return` and `throw` in the function's own body. Nested functions are traced only when they are targets themselves. More than 400 probes refuse with `too-large`; changed lines outside any function refuse with `no-function`.
- **Edits.** The plan is a list of insertions at UTF-16 offsets. Conditions become `__beuveTrace.branch(frame, id, (cond))`, values pass through the recorder unchanged, loops are wrapped together with their labels and their bodies count iterations, and the body becomes `const __beuveFrame = enter(id, [args]); try { … } catch (e) { throw unwind(frame, e) } finally { exit(frame) }`, so exceptions from callees end the frame too. Expression-bodied arrows become blocks. `applyEdits` orders insertions at one offset so wrappers nest. **No insertion contains a line break**, so the instrumented module has the original's line numbers and needs no source map; probes carry their head line, which is the diff's head line.
- **Running.** `TraceRunner.run(request)` is the port; `createVitestTraceRunner` runs one `vitest run` per probe with Node (`process.execPath` with `ELECTRON_RUN_AS_NODE` in the app), no shell, the CLI script found from `node_modules/vitest/package.json`'s `bin`, an allow-listed environment plus `CI=1` (no new snapshots), its own process group (killed on timeout, cancellation and exit), and the request's timeout. Everything it writes goes to a fresh directory under a beuve temp root that is removed afterwards: a generated `vitest.config.mjs` that imports and merges the project's nearest `vitest.config.*`/`vite.config.*`, `run.json` with the instrumented text, a setup module, caches and the JSON report. That directory links `node_modules` to the dependency root (the user's checkout, which has its dependencies installed), and the generated plugin retries unresolved bare imports from worktree files there. The config forces `watch`, `update`, coverage, typecheck, `cache` and `fsModuleCache` off and `cacheDir` into the temp directory. The transform throws when the file on disk differs from the text the plan was made from, which fails that test file instead of tracing stale code. The integration test checks that the worktree is byte-for-byte unchanged.
- **Recording.** The setup module embeds `createTraceRecorder`'s source (`String(fn)`; the function is self-contained, which a test checks in a bare `vm` context; it also survives esbuild bundling, minified or not) and installs it as `globalThis.__beuveTrace`. `beforeEach` attributes events to the test (file and titles); `afterEach` appends one JSON line per test to `events-<pid>-<thread>.jsonl`, so workers never share a file. Outcomes come from Vitest's JSON reporter. `parseTraceRecord` and `parseVitestReport` check and bound everything they read. `buildTraceTimelines` joins events with the plan's probes into one timeline per test: `enter`, `branch` (`if`/`ternary` taken, `switch`/`catch` value, `case`/`default` entered), `loop` (iterations), `return` (value, or implicit) and `throw` (value, and whether it passed through from a callee), each with its line, call depth among traced functions, and whether its own lines are in the hunk. `runTraceProbe(request, runner)` composes instrument, run and reduce.
- **Value summaries** are one-line previews (`{ type, preview }`) made without running program code: properties are read through descriptors only (accessors show as `[Getter]`), proxies are detected with `util.types.isProxy` and never inspected, built-ins are read through intrinsics captured at setup (`Map` size and entries, `Date#toISOString`, `RegExp` source, typed-array length), no `toString`, `toJSON` or `Symbol.toStringTag`, cycles show `[Circular]`, and limits apply: depth 2, 5 items per container, 60 characters per string, 160 per preview, 2,000 events per test and 50 per probe per call (the rest counted as `dropped`). Values are summarized when recorded, so later mutation doesn't change them.
- **Test selection** is static and cheap: `selectTests` runs a changed test file itself; otherwise it takes test files named after the changed file (`foo.test.ts`, `foo.spec.tsx`, `__tests__/foo.ts`, nearest directory first, ahead if they also import it), then tests importing it directly, then tests reaching it within four import hops, three files at most. `buildImportGraph` resolves relative specifiers (including `.js` written for `.ts`, missing extensions and `index` files) in sources main reads at the head. When that finds nothing, main falls back to, in order: LSP references to the enclosing function filtered to test files (ADR 0021's multiplexer), then asking the reviewer. Coverage-based mapping per head is deferred: its first run costs a full test-suite run.
- **Trust.** Tests run only after the reviewer allows it for that repository, explicitly, once per repository (stored by main), and never automatically: not on session load, not from the preliminary review, and not from MCP unless already granted (the tool then fails with `untrusted` and says how to grant it). The request type carries `trusted: true` and the runner refuses anything else. Trusting a repository means trusting its tests, configs and the user's installed `node_modules`; ADR 0017's binary policy is unchanged.

## Consequences

The spec's 200 ms holds only for a warm Vitest instance; with one process per probe the realistic latency is 0.6 to 1.2 s for small suites and more for projects with heavy setup. That is acceptable for an explicit keypress with a running state, and the timeline is exact. **A warm runner is deferred**, behind the same port: a driver process per (worktree, dependency root) that calls `createVitest` once, then per probe rewrites `run.json`, calls `invalidateFile` and `runTestSpecifications`, with ADR 0017's idle timeout and crash budget. It was not built now because Vitest's Node API changes between majors (Vitest 5 deprecates `createVitest`'s mode argument) while the CLI flags used here are stable, and because a resident process keeps repository code running between keypresses, which needs the lifecycle and trust UX settled first.

Accepted limits: Vitest only (Jest and others need their own runner); one instrumented file per probe; a root config's `test.projects` don't inherit beuve's setup file; concurrent tests (`test.concurrent`) and async interleaving can attribute or nest events loosely (frames are explicit, depth follows the synchronous call stack); generators and `await` points are not events; `&&`, `||`, `??` and optional chaining are not branches; destructured parameters of arrow functions show as unavailable; the dependency root's `node_modules` may not match the head's lockfile; tests can still write files themselves (beuve can't sandbox them); the recorder must stay self-contained, so coverage instrumentation of beuve's own tests would break the `vm` test; and test selection misses dynamic imports with computed specifiers and alias imports (`#pkg/…`, `@/…`) unless main passes resolved edges.

## Amendment (2026-10-31): the scratch `node_modules` is a directory of links

Every probe wrote into the user's clone, against ADR 0088. Vite bundles the generated config and writes the bundle to `<nearest node_modules>/.vite-temp/` beside it (`loadConfigFromBundledFile`, Vite 6 and later; Vite 5 writes beside the config). The scratch directory's `node_modules` was one link to the clone's `node_modules`, so `.vite-temp/` was created in the clone and a file briefly written there. Separately, Vitest 3.2 and later copy `annotate` attachments to `<root>/.vitest/attachments`, inside the worktree.

- **The scratch `node_modules` is a real directory** holding one link per entry of the dependency root's `node_modules` (scoped directories such as `@scope` are linked whole). Vite's nearest `node_modules` is now in scratch, so `.vite-temp` lands there and is removed with the run directory. This works for every Vite version, because it changes where Vite writes, not how it loads the config.
- **Dot-entries are not linked.** They are caches and tool state (`.vite-temp` left by the user's own runs, `.vite`, `.cache`, `.vitest-cache`), which would lead writes back into the clone, or `.bin` and `.pnpm`, which nothing needs: packages resolve through their real paths, so pnpm's and Yarn's links still find their dependencies in the clone.
- **`--configLoader runner` was rejected.** It also avoids the temp file, but the flag exists only in Vitest 3.1 and later, so the runner would have to gate it on the reviewed repository's Vitest version, and it changes how the project's own config is evaluated (Vite's module runner instead of a bundle, experimental in Vite), which can break configs that load today. The links leave config loading as it was.
- **The generated config also sets** `attachmentsDir` to the run directory and turns off `server.debug.dump` and `load` (otherwise `<root>/.vitest-dump`). Older Vitest ignores keys it doesn't know.
- **The integration tests snapshot both trees** (every path with its kind, size, modification time and link target, without following links, `node_modules` and dot-entries included) before and after a probe whose project config loads a scoped plugin from the clone, and after one whose tests try to write a snapshot, an inline snapshot and an attachment; both must be unchanged.

Remaining writes beuve doesn't control: a test's own file writes (as before), browser-mode screenshots, and tools in a project config that write relative to `process.cwd()` (the project root inside the read-only checkout, where they fail).

## Amendment (2026-11-01, ADR 0089, 0090): the checkout's own dependencies

- **The dependency root is the checkout once beuve installed it**: when the head checkout's install finished (ADR 0089) and it has a top-level `node_modules`, the probe resolves packages there, so it runs against the reviewed head's own lockfile. Otherwise it uses the user's clone, as before. The scratch `node_modules` stays a directory of links, so a probe still writes into neither.
- **Trust** is now the one grant of ADR 0090, which also covers dependency installs, install scripts included; the request type's `trusted: true` is unchanged.
