# 0125. Note drafting requests run outside the chat

- Status: Accepted; amends [0055](0055-review-folded-into-chat-with-verification.md) ("every model call is a chat request")
- Date: 2026-11-10

## Context

The reviewer wants help writing review notes: "expand on this" (turn a terse idea into a note the author can act on), and later "review my review" (catch questions the code already answers) and "summarize my review" (an opt-in summary for the top of the posted review). ADR 0055 made every model call a chat request: queued per session (ADR 0057), stored in `chat_messages`, and built from the conversation, its mentions and its focus.

That is the wrong home for drafting. A note is written for the author of the change, who never sees the reviewer's chat; a prompt built from the chat would carry its context (earlier questions, half-formed theories, beuve's own findings) into text the author must understand without it. Running drafts through the chat would also put requests that aren't questions into the transcript and behind a minutes-long `/review` in the queue, and every later question would see them as history.

## Decision

- **Drafting is a one-off model request**, outside the chat: one IPC request per draft (`ura:expand-note` first), answered with the text or a typed failure. Nothing is stored and nothing joins the chat queue or its history. It is cancellable with `request:cancel`, like `github:open-pr`, and a new request for the same note replaces one in flight.
- **Its context is the change and the draft, nothing else.** The prompt holds the note's severity, title and body, its anchor, and the diff hunks of the anchored file that touch or neighbour the anchored lines (or the file's own hunks for a file note, a bounded slice of the diff for a whole-change note), at the note's head, bounded like the chat's diff. Diff and draft are fenced as untrusted (`fenceUntrusted`). It never includes the chat transcript, other notes, beuve's findings, the pull request's description (as for `/summarize`, ADR 0056) or the reviewer's mentions.
- **No repository access.** The run gets a scratch directory as `cwd` (as Settings' Test does) and no `tree`, so a checkout-reading adapter has nothing to read and the answer can only lean on what the prompt shows. The note is about the lines on screen; reading the repository would invite claims the author cannot check against the diff.
- **The model** is resolved by a new role, `draft` (ADR 0070's per-role models), which falls back to the default entry like the others; effort `low` and a two-minute timeout by default.
- **The instructions**: write the note for the change's author, in the reviewer's voice and language; keep the reviewer's point and severity; add only what the shown code supports; never invent a problem, mention a tool, a model, a chat or anything outside the shown diff; return only the note's Markdown body.
- **The reviewer decides.** The result replaces the body field's text as an ordinary edit the reviewer can undo or rewrite; it is never staged, saved or posted by itself. The title and severity stay the reviewer's.
- **Later drafting requests** ("review my review", "summarize my review") follow the same rules, each with its own channel and its own narrow context; each is added when it is built.

## Consequences

- CLAUDE.md's rule "every model call is a chat request" gains this exception: note drafting. Anything else that talks to a model still goes through the chat.
- A draft costs a model call that leaves no trace in the transcript, so the reviewer can't scroll back to it; the text lives only in the note.
- Without repository access the model can misread code it only sees in a hunk; the reviewer reads the result before staging, as with anything beuve writes for them.
- A second request path to the model means a second place to keep the adapter's failures readable; it reuses the chat's `describeModelError`.

## Amendment (2026-11-10): as built

- The diff is the whole change at the note's head (fork point to `headSha`), not the review's interdiff, so a note on an older head or a reviewed-up-to-date session still sees its hunks. A line note gets its file's hunks within 20 lines of the anchor (the nearest one when none is), nearest first while they fit half the chat's prompt budget; the prompt builder and the selection are in `src/internal/chat` (`build-note-draft-prompt.ts`, `select-note-hunks.ts`) because they share the chat's fencing and budgets; nothing there touches the chat's queue or tables. Main's side is `src/main/drafting/`.
- The renderer names a note's requests `expand-note:<note>` (the composer's is `new`), and main supersedes a `note-draft` scope only by the same `requestId`, so the composer and an edit form can expand at once.
- The forms' Expand is `beuve-note-expand`, which asks with a composed `beuve-note-expand-request` that `beuve-review` answers; it replaces the body by selecting it and inserting the text (`execCommand('insertText')`), which keeps Chromium's undo stack. Review ▸ Note ▸ Expand Draft (`expand-note`, no chord) runs the Expand of the note form last focused.

## Amendment 2026-11-11: "✨ Flesh out", at the start of the last row

"Expand" read as making the form bigger. The button is "✨ Flesh out" (the menu item Review ▸ Note ▸ Flesh Out Draft, the model role "Flesh out note"); ✨ marks it as the model's help, so `praise` became 🎉 (ADR 0131 amendment). It sits at the start of the form's last row, apart from Cancel and Stage or Save at the end, and while it runs it shows "Fleshing out…" and Stop, never a second Cancel. The code keeps the names `expand-note`, `ura:expand-note` and `beuve-note-expand`.

## Amendment 2026-11-28: Autoedit: body and suggestions

A note now carries suggestions (ADR 0162), and "✨ Flesh out" rewrote only the body, so a reviewer who wrote "rename to `retryBudget`" got prose saying so and still had to write the code. The button becomes **✨ Autoedit**, and one request revises the body and the suggestions together.

- **Names.** The button is "✨ Autoedit" ("Autoediting…" and Stop while it runs), the menu item Review ▸ Note ▸ Autoedit Draft (`autoedit-note`, title "Autoedit Note Draft", no chord), the model role "Autoedit note" (still the `draft` role). Since the answer's shape changed, the code names change with it: `ura:autoedit-note` (`AutoeditNoteRequest`, `AutoeditedNoteView`), `beuve-note-autoedit` and its `beuve-note-autoedit-request`, `drafting.autoeditNote`, request ids `autoedit-note:<note>`. The prompt builder keeps its name (`build-note-draft-prompt.ts`).
- **The request** sends what it sent before (label, Blocking, title, body, anchor, at the note's head) plus the form's suggestion fields as they hold now: each one's form `key`, path, lines and current text. A field still reading its lines holds the request back ("Wait for the suggestions to read their lines.").
- **The prompt** names the suggestions s1, s2, … in form order, each with its lines, the text those lines have at the head (main reads it from the head blob, since the domain reads no files) and its replacement, all fenced as untrusted like the diff; the hunks are chosen as before. It refuses suggestions whose text together is over one file's share of the chat budget. The instructions add: add or change a suggestion only when the draft asks for a concrete code change, or when an existing one must change to match the revised text; never invent a change; suggest only on the lines shown; a suggestion can't be removed, so leave out every one not changed. Everything else in the instructions stands.
- **The answer** is one JSON object, `{ body, suggestions: [{ id?, path, startLine, endLine, replacement }] }`, asked for in the prompt and read with `runText` rather than the port's structured `run`, so that one malformed suggestion is dropped alone instead of failing the answer. Main unwraps a fenced answer, validates it with zod (`parseAutoeditAnswer`), unwraps the body as before, and fails with `invalid-output` when it isn't JSON or has no body.
- **Main checks every suggestion** (`checkAutoeditSuggestions`) and drops what fails, counting the dropped ones for the form ("2 invalid suggestions left out"): an `id` must be one of the draft's and revise it only once; the lines must lie in what the prompt showed (each shown hunk's head lines, as far as the hunk was shown, and each existing suggestion's lines; an insertion may sit right after a shown run); the file must be text at the head and hold the lines (`checkSuggestionRanges`); a replacement is at most 64 KiB, an insertion adds a line, and the note stays within 500 suggestions (`uraSuggestionLimits`); and no two of the note's resulting suggestions may overlap, as `validateUraItem` defines it. Revisions are placed first, against every other suggestion as it was and as revised; new ones after, in order. A revision that changes nothing is no change.
- **The model can't delete.** A suggestion the answer leaves out stays exactly as it was, and so does one whose revision is dropped: an autoedit only revises and adds. Removing a suggestion stays the reviewer's Remove.
- **Nothing is staged.** The answer only fills the form: the body's text is replaced as before (one undoable edit in the textarea), each revised field is replaced by a new one holding the revised text under a fresh key (keeping the stored suggestion's id, so saving keeps its identity and postings), and each new suggestion becomes a field at the end. The form's owner, which keeps the list of fields, applies them from a composed `beuve-suggestion-fields-replace`.
- **Undo autoedit.** After an autoedit the form shows "Undo autoedit" beside ✨ Autoedit. It restores the body and every field as they were before the request, removing the fields it added, from a snapshot taken when the request was sent, not from each field's own CodeMirror history (which a replaced field doesn't have). It is offered until the reviewer edits the form: typing in the title, body or a field (fields report `beuve-suggestion-field-edit`), or a field added or removed by anything but the autoedit (the button watches the form's fields); a new autoedit, saving, cancelling or closing the form ends it too. Label and Blocking are not part of the snapshot, since an autoedit never changes them.
- Unchanged: no repository access (a scratch `cwd`, no `tree`), the `draft` role at effort `low` with a two-minute timeout, cancellable with Stop or `request:cancel`, and a newer request for the same note supersedes one in flight.
