# 0073. A streaming Markdown renderer for chat answers, on WHATWG streams

- Status: Accepted; amends [0031](0031-read-only-qa-chat.md), [0055](0055-review-folded-into-chat-with-verification.md) and [0072](0072-chat-message-parts-and-stream-protocol.md)
- Date: 2026-10-30

## Context

Chat answers were parsed by a small subset (`parseMarkdownSubset` through `parseAnswerMarkdown`: paragraphs, flat lists, unhighlighted code, headings as bold paragraphs), and every text delta re-parsed and re-rendered the whole answer. Answers use more than that (nested lists, tables, quotes, real headings), a long answer did quadratic work, and an unclosed `**` or fence flickered through literal syntax. ADR 0072 gave each text part a `ReadableStream<string>` (`textPartStream`) so a renderer can consume text as it is written. The chat UI survey compared Streamdown, streaming-markdown (smd), Deep Chat and marked/micromark with a re-render: none keeps citations as validated pills or builds DOM without HTML strings, and each would be a dependency to sanitise and audit. A block-committing renderer is a few hundred lines.

## Decision

- **Pipeline.** `textPartStream(…).pipeThrough(new MarkdownBlockStream()).pipeTo(sink)` with the drawer's `AbortSignal`. `MarkdownBlockStream` (a `TransformStream<string, MarkdownChunk>`) splits `rest + delta` with `splitMarkdownBlocks`, a line-based state machine over the top-level blocks: a block is emitted once, parsed, when later text can no longer change it (its closing fence, a heading or rule line, a blank line, or the first line of the next block). What stays open is re-parsed provisionally and emitted as the `tail`, which replaces the previous one. On close the rest is split as final. The sink (`MarkdownView`) inserts each finished block's nodes once and never touches them again; only the tail's nodes are replaced. A block's extent depends only on its own lines and the line after it, so the streamed result equals `parseMarkdown` of the whole text; tests feed a sample answer split at every offset and in pieces of 1 to 64 characters and compare the trees.
- **One parser.** `parseMarkdown` is `splitMarkdownBlocks` (final) plus a block parser; `classifyMarkdownLine` is shared by both, so they agree on every line. Stored messages, summaries, `/summarize` abstracts and finding titles and bodies render through it with `MarkdownView.show`, which reuses the nodes of unchanged blocks that cite nothing: when the validated answer replaces a streamed one, only blocks with citations (or that changed) are rebuilt and highlighted code stays.
- **Subset.** Paragraphs (lines joined), ATX headings (`#`–`######`, closing hashes dropped), fenced code (backticks or tildes, info string's first word, may be unclosed), bullet and ordered lists (an ordered list keeps its start; a change of marker starts a new list; an item line deeper than the list's first item nests, and other lines belong to the current item, dedented by its content column), block quotes (nested), rules, and GFM tables (a one-line pipe paragraph followed by a delimiter row with as many columns; alignment; rows padded or cut to the header). Inline: backslash escapes, code spans, `*`/`_` emphasis and strong (`_` never inside a word, so `snake_case` and paths stay text), links with an optional title, `<url>` autolinks, bare `http(s)://` URLs (trailing punctuation and unbalanced `)` excluded), and `[[path:a-b]]` citation markers as their own node. Not supported, and left as text: raw HTML (always escaped), setext headings, indented code blocks, reference links, images (`!` then the link), footnotes, task-list checkboxes, strikethrough, hard line breaks, lazy continuation lines of quotes and list items.
- **Streaming without flicker.** The tail is parsed with `isProvisional`: an unfinished last line that is only block syntax (`#`, `-`, ` ` ``, `|--`, `1.`) is hidden; a lone pipe row waits for its delimiter row instead of showing as a paragraph; an unclosed code span or `**` (or `*`/`_` after a space) runs to the end; a link being written shows its label, never its syntax; a citation marker being written is hidden (as ADR 0031 did); a trailing delimiter or backslash waits. An open fence renders its code as plain text as it arrives.
- **Safety.** The DOM is built with `createElement`, text nodes and `textContent` (`createMarkdownNodes`); model text never reaches `innerHTML`, a template's HTML, or an attribute other than a link's `href`/`title`. A link is rendered only for an absolute `http:` or `https:` URL, normalised by the URL parser (`safeHrefFrom`); `javascript:`, `data:`, `file:`, protocol-relative and relative targets keep only their text. A link carries `data-action="link"` for the drawer's delegated click listener, which emits `beuve-open-link`; main opens GitHub links and refuses others (ADR 0040), and the window never navigates. The app's own line targets are the citation markers: while an answer streams every well-formed marker is dimmed text, and once it is final a marker of the message's validated `citations` becomes the same pill (built from the drawer's Lit template), any other marker stays text (ADR 0031, 0072). The CSP is unchanged.
- **Code.** A closed fence renders through `beuve-sheet-code` in a new `compact` mode (the diff view's `@pierre/diffs` with beuve's Alabaster themes, ADR 0025, 0067: no line numbers, selection or token clicks), with the language picked from the info string by file extension (`snippetPathFrom`); unknown languages and an unclosed fence are plain monospace. The block shows its text while the library loads, so it keeps its height. Only the closed block is highlighted, once.
- **Where it lives.** All of it is `src/ui` (the parser is not standard-library material, ADR 0002): `classify-markdown-line.ts`, `split-markdown-blocks.ts`, `parse-markdown.ts`, `parse-markdown-inline.ts`, `table-cells-from.ts`, `table-alignments-from.ts`, `safe-href-from.ts`, `markdown-block-stream.ts` (pure, Vitest-tested without a DOM) and `create-markdown-nodes.ts`, `markdown-view.ts` (DOM). `parseAnswerMarkdown` is gone; `parseMarkdownSubset` still serves insight cards, inline titles and pull request bodies.
- **Status line.** Main pushes what a question's or `/summarize`'s model is doing as the status's `activity` (`describeChatActivity`): `Asking <model>` once the role's model is resolved, then `<model> is thinking`, `<model>: read src/a.ts:1-40` for a tool call, `<model> is writing`. `<model>` is the resolved entry's name (`Claude Code` for both Claude Code kinds, else the registry label), so the drawer no longer says "Asking Claude Code…" for another model.
- **Verification progress.** `/review`'s verification pass now reports its model's progress (`ReviewProgress` `model` events carry `pass: 'review' | 'verify'`), so its tool calls become parts like the first pass's, and its status says `Checking n findings against the code: <tool>`. This replaces ADR 0072's consequence that it showed none.

## Consequences

- Rendering a streaming answer is linear in its length: each delta re-parses only the open block. Text selected in a finished block survives later deltas; a selection in the tail does not.
- Answers show real headings, nested lists, quotes, tables and highlighted code, live and stored alike. Each highlighted block is one `@pierre/diffs` `File`; a very code-heavy transcript costs what as many small sheets would.
- The Markdown subset is ours to maintain and grows by test cases; anything outside it stays visible as text rather than disappearing. A block that turns out different once the final text arrives (citations validated, unknown paths turned into code) is rebuilt, which is the one moment a finished block changes.
- Links outside GitHub can't be opened from the chat (main's rule), only read in their tooltip.
