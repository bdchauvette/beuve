# 0041. Trace probes in the app: trust, channels, cancellation and the MCP tool

- Status: Accepted
- Date: 2026-10-28

## Context

ADR 0036 built the instrumented-Vitest probe and left four things to main and the renderer: where the reviewer's approval to run a repository's tests lives and what it is keyed by, how a probe reaches the renderer and MCP, how it is stopped, and which clone supplies `node_modules`. They constrain later work (a warm runner, other test frameworks) so they are recorded here.

## Decision

- **Trust is per repository, explicit, and stored in `settings.json`** (ADR 0033's file, key `traceTrustedRepositories`), as `{ "<real path>": { trustedAt, remoteUrl? } }`, written through `updateSettingsFile` so other keys survive. The key is the repository's real path (`realpath` of git's top level). When the approval was made the repository's `origin` URL (else its first remote's, as configured, before `insteadOf`) is recorded; an approval holds only while the path is the same and, if a URL was recorded, the repository still has that URL. A path that now holds another project, or whose remote was swapped, is untrusted again. Nothing is trusted by default, malformed entries read as untrusted, and no code path runs a probe without `status().trusted`: main checks it before reading blobs or touching the runner, and the runner independently refuses a request without `trusted: true` (ADR 0036). Pull request sessions are keyed by their local clone, which is where the tests run (ADR 0037).
- **How the reviewer grants it.** The first `r` in an untrusted repository shows an inline prompt in the card's portal area: it says the probe runs the repository's test code and Vitest config on this machine with the user's access, names the path, and offers "Trust and run" and "Cancel" (focus starts on Cancel). Agreeing stores the approval and runs the probe. `/trust` and `/untrust` in the chat do the same for the open session's repository and `/help` lists them. The renderer-only `trace:get-trust` and `trace:set-trust` channels carry this; nothing the model or an MCP client writes can call them.
- **`beuve_run_trace_probe` never prompts.** Without approval it fails with `untrusted: …` telling the agent a human must trust the repository in beuve (the prompt, or `/trust`). Its input is `{ sessionId?, path, line, testNamePattern? }` (`testName` in the earlier stub is renamed). `line` and every line of the result are 1-based head lines. The result is structured content `{ sessionId, headSha, path, testFiles, testsFailed, functions, timelines, durationMs }`; failing tests are not an error, the trace comes back with `testsFailed: true`. Other failures are `<kind>: <message>` tool errors. A probe an agent starts is one of the session's probes (below) and pushes no renderer events.
- **Channels.** `trace:run { sessionId, path, line, testNamePattern? }` acknowledges with a run id and works in the background; the outcome is pushed as `trace:status` events carrying the request's path and line so the portal ignores stale ones: `running` (with the selected test files), `completed` (with the trace) or `failed` with a kind: `untrusted`, `no-tests-found`, `not-vitest`, `unsupported-language`, `no-function-at-line`, `file-unavailable`, `too-large`, `timeout`, `cancelled`, `runner-failed`, or `test-failed-with-trace` (tests ran and some failed; the trace is attached and shown). `trace:cancel { sessionId }` stops the probe in flight.
- **One probe per session.** A second `trace:run` while one runs is `refused`, except that a probe already told to stop is awaited first, so `r` on another hunk (which cancels, then runs) never races the process that is dying.
- **Cancellation** aborts the probe's `AbortSignal`, which the runner turns into SIGTERM then SIGKILL of the Vitest process group: Escape or closing the portal while it runs, a head change (`onHeadMoved` reaches `observeHead`, like the chat and review), and `dispose` on quit, which waits for the processes. The runner now also honours an abort that arrives between its first check and the process starting (found by an integration test: such a run used to ignore it until the timeout).
- **Timeout** is 30 s per probe (`trace.timeoutMs` overrides it in tests), reported as `timeout`.
- **Dependencies come from the clone.** The dependency root is the repository's top level (the session's `repoPath`, or for a pull request its clone); the tests run in the session's head worktree (ADR 0020). Vitest missing there is `not-vitest`; no setup is attempted.
- **Hunk and test selection.** The traced functions are those enclosing the changed head lines of the hunk around the requested line plus the line itself. Tests are picked statically from the head's blobs read through git (never the checkout): test files named after the file, then importers, then four import hops, three files at most. ADR 0036's LSP-references and ask-the-reviewer fallbacks are not built: `no-tests-found` says to name a test file beside the source.
- **Related follow-ups.** `beuve_read_human_review`'s structured content gains `pullRequest { number, title, url, state, author }` for pull request sessions (additive, `beuve.ura/1` is unchanged; the XML is not). The Q&A chat prompt gains an optional `intent` (a pull request's title and body) rendered fenced as untrusted text after the change summary, bounded by `maxIntentChars` (6,000) and reported as `intentTruncated`.

## Consequences

Measured in the app on a 4-core container, one probe on a four-test file takes 0.65 to 0.70 s from keypress to timeline, and the first one after granting trust 0.8 s (a cold Vitest process each time; the warm runner stays deferred). Revoking trust or moving a repository is a settings edit, and a user who copies `settings.json` to another machine finds nothing trusted there unless the path matches too. Trusting a repository trusts every later commit of it, including a pull request's head, because the approval is for the repository, not a commit: reviewers of hostile pull requests should not trust a clone they review untrusted code in. The approval does not extend to the language servers (ADR 0017) or to other test runners. Jest and other frameworks need a runner behind the same port and probably their own `not-vitest`-style failure.

## Amendment (2026-11-01, ADR 0089, 0090): one grant for tests and installs

- **The approval is the one trust grant** (ADR 0090): "run this repository's tests and install its dependencies, including their install scripts". It moved from `settings.json` (`traceTrustedRepositories`) into the trust domain's `trust_grants` table as a `repository` scope (path plus recorded remote, matched as before); earlier entries are moved on first use. The channels are `trust:get`, `trust:set`, `trust:list` and `trust:remove` (were `trace:get-trust`, `trace:set-trust`, `trace:list-trust`, `trace:remove-trust`), still renderer-only. Review › Trust Repository… opens the prompt; `/trust` and `/untrust` remain.
- **Dependencies come from the checkout when installed** (ADR 0089, ADR 0036 amendment), else from the clone as this ADR decided.
- `beuve_run_trace_probe` still never prompts, and an agent still can't grant trust.
