# 0054. Commit pairing across rebases, and stack-aware fork points

- Status: Accepted; amends [0010](0010-git-cli-and-interdiff.md) and [0012](0012-checkpoint-base-and-review-composition.md)
- Date: 2026-10-30

## Context

Teams that stack pull requests rebase them constantly: a lower PR changes, is force-pushed or merges, and every PR above it moves to a new base. ADR 0010's interdiff replays the reviewed range onto the new fork point, which hides upstream changes, but three cases still went wrong or said too little:

- **The fork point itself lies.** After a parent is squash- or rebase-merged and the child is retargeted to `main` without rebasing, the merge-base with `main` is the old fork, so the parent's commits (now on `main` under other SHAs) showed as the child's changes. The same happens when a parent is force-pushed and the child is not rebased yet.
- **Conflicts threw everything away.** When the range replay conflicted (often because a commit moved from the child into the parent and was adapted there) the reviewer got the full PR again.
- **No commit-level story.** The reviewer couldn't see which reviewed commits survived, were amended, were dropped or are new, the way `git range-diff` and Gerrit's patchsets show it.

## Decision

- **Pairing (`pairCommits`, `computeCommitPairs`).** Both ranges (checkpoint `base..head`, and new fork point `..head`) are read with one `git log -p --unified=0 --no-merges` each, fed to `git patch-id --stable`. Commits pair first by equal patch-id (positionally for duplicates; empty commits by subject), then greedily by descending score over the Dice coefficient of their changed lines (multiset of path, sign and trimmed content) plus 0.3 for an equal subject, ties broken by relative position. A fuzzy pair needs a Dice of 0.5, or 0.2 with an equal subject; the rest are `added` or `dropped`. Output is in `git range-diff`'s order. Each `modified` pair gets an interdiff of its own: the old commit replayed onto the new commit's parent (`merge-tree`), diffed against the new commit; an empty one makes the pair `unchanged`.
- **Why not parse `git range-diff`.** We checked it on the same fixtures (the tests still assert agreement): it has no machine format, so pairing lines are padded, abbreviated (`--abbrev`, `core.abbrev`) and end in a free-form subject that may contain its own delimiters; it prints the old subject on `!` lines; and it yields neither scores nor tree interdiffs. We need each commit's patch anyway for `+/−`, hunk attribution and the per-pair interdiff, so parsing range-diff would add a spawn and a brittle parser for the one thing (pairing) that is a few dozen lines of pure code. Its `=` is patch-id equality, which we compute the same way; its fuzzy step (Hungarian over diff-of-diff sizes with a 60% creation factor) is approximated by the greedy Dice match, which is easier to explain in a tooltip.
- **Stack-aware fork point (`findStackForkPoint`).** The review's base is the newest first-parent commit of `mergeBase..head` that is either (a) **already upstream**: merging it into the base tip is a no-op (`merge-tree --merge-base=<mergeBase> <baseTip> <X>` gives the base tip's tree), which covers squash-merged, rebase-merged and cherry-picked parents whatever their SHAs, or (b) a **reviewed base**: the latest checkpoint's base, still an ancestor of the head, which covers a force-pushed parent the child wasn't rebased onto. Otherwise it is the merge-base. Containment is checked on the oldest commit first and binary-searched only when that one is upstream, so the common case costs one `merge-tree`. Full reviews, interdiffs, up-to-date views and `session:mark-reviewed` all use this fork point, so the checkpoint records the base the reviewer actually saw. Patch-ids identify a rebase-merged parent commit by commit; a squash of several commits has no matching patch-id, which is why containment, not patch-id, decides the fork point.
- **Range replay first, commit-pair replay on conflict.** The whole-range three-way replay stays primary: it is one merge, and it is exact when the author squashes, splits or reorders commits, where pairing degrades to added/dropped and a per-commit replay would show already-reviewed lines as new. Only when it conflicts does `computeInterdiff` replay the paired old commits one by one in the new order onto the new fork point (`replayCommits`: `merge-tree` per step, intermediate trees wrapped in dangling `commit-tree` objects with a fixed identity, because git before 2.45 merges only commits). If that is clean the outcome is `rebased` with `replay: 'commit-pairs'`; otherwise it is ADR 0010's `fallback`. Dropped commits are not replayed, so a commit moved into the parent disappears instead of conflicting.
- **Contract (additive).** `ReviewView` gains `commitPairs` (interdiff only; id = new sha, else old), `fileAttribution` (per file, the pairs that touched it and, aligned with its hunks, the pairs whose new commit produced those lines), and `forkPoint` (`already-upstream | reviewed-base`, the merge-base it replaced, skipped commits). The `rebased` outcome gains optional `replay`. Attribution is pure: each new commit's changed lines are carried to head coordinates through the later commits' zero-context hunks (renames followed, rewritten lines go to the rewriter) and matched to the hunk's added lines and deletion points.
- **UI.** `src/ui/beuve-commit-pairing.ts` lists pairs (old → new sha, kind chip, subject, `+/−`), one tab stop with `j`/`k`/arrows/`Home`/`End`, `Enter`/`Space` to filter, `Escape` to clear, and emits `beuve-commit-pair-filter { pairId | undefined }`. Wiring it into the diff stream is left to the stream's owner.
- **Limits.** 100 commits per range (beyond that `commitPairs` is omitted), 25 per-pair interdiffs per review (the rest say `too-many-pairs`), 200 first-parent commits inspected for the fork point. Merges are skipped in pairing and the fork search follows first parents. Containment assumes that once a commit is upstream its ancestors are too. Per-pair interdiffs and the commit-pair replay need git 2.40.

## Consequences

A stacked PR keeps showing only its own changes through parent rebases, force-pushes, squash merges and retargets, and a conflicting restack no longer forces a full re-review when the conflict came from a commit that left the PR. Every interdiff costs about four more git spawns (two `log`, two `patch-id`), two more per modified pair and a few for the fork point; results are cached with the diff. A never-reviewed child whose parent was force-pushed with real changes still shows the old parent commits, since nothing tells beuve where its own work starts (GitHub's old base SHA could, later). The reviewed-base rule trusts the checkpoint: a reviewer who signed off on a branch including a parent commit won't see that commit again. The dangling replay commits are left for `git gc`, like `merge-tree`'s trees.
