# 0111. Language-server diagnostics in the review UI, and configurable language servers

- Status: Proposed
- Date: 2026-11-03

## Context

A reviewer in an IDE sees exactly where a type or lint error is. In beuve they see nothing, so they cannot tell whether a change compiles without leaving the app. ADR 0106 removed the only reader of language-server diagnostics (the MCP tools), and the code that served them was deleted from `src/main` but its machinery in `src/internal/lsp` is kept. The reviewer wants diagnostics back, in the review UI, for any language whose server speaks LSP. The immediate need is Go, Python is next, and custom servers should be a matter of configuration. No autofix: the client stays read-only (ADR 0016).

What exists today limits this:

- A `ServerDefinition` is already data (ADR 0017), but the registry holds one built-in entry, TypeScript, and maps each file extension to one server.
- Servers come only from beuve itself: its bundled TypeScript pair, or a name looked up on `PATH`. The workspace's own binaries and its own TypeScript are off by default, because a reviewed branch can plant an executable there (ADR 0017).
- Dependencies are the reviewer's to install, in the terminal panel (ADR 0095). That ADR also left open where a file of custom server definitions would live, with one constraint: in the reviewer's own settings, not in the reviewed repository, "since a server is a program beuve starts".

## Decision

### What the reviewer sees

- Diagnostics from the language servers appear on the head side of the diff, from beuve's checkout of the session head (ADR 0020), like hover and go to definition (ADR 0097). A line with diagnostics gets a severity marker; the message, code and source (which server) show in a popover. The file header carries a count, including diagnostics outside the shown hunks. Nothing marks the base side.
- Diagnostics are shown for the lines of the file, not compared against the base. Pre-existing problems on lines the change touches appear too. Comparing base and head is a possible refinement if that proves noisy; it needs a second checkout and server pass and is not part of this ADR.
- No code actions, quick fixes or edits (ADR 0016). Staging a diagnostic as a review note is a natural follow-up and is not decided here.
- Results show as "checking…" until the servers settle. ADR 0016's settle rules (pull when offered, else the first push report after the latest sync plus a quiet period, with a deadline) decide when "checking" ends. Step 1 delivers one answer per file, from `lsp:diagnostics`, which resolves when the servers have settled or the deadline passed; the renderer asks about each file once per head, a few at a time. Pushing partial results as they arrive, so a slow server shows what it has so far, is a refinement for later, not part of step 1.
- A servers' view of the checkout is only as complete as what is installed there. The popover says so once, in general words ("from `<server>`, in beuve's checkout; install dependencies in the terminal, then Review › Restart Language Servers"), rather than detecting per ecosystem which dependencies are missing (the table ADR 0095 dropped).
- **Only the head.** Diagnostics appear in the diff and in sheets at the session head's commit. A sheet pinned to an older commit (ADR 0067) shows none; it shows a small information icon, styled as a heads-up and not as a warning or error marker, whose tooltip says diagnostics are only available at the head. When the head moves, a sheet that was at the head is older, and gets the same icon.

### Servers

- **Several servers per file.** The registry maps a file to every server that claims it. Diagnostics are the union over those servers, each tagged with its server id, so a type checker and a linter can both report. Hover, definition, call hierarchy and symbols use the first matching server that advertises the capability, in registry order.
- **Roots.** A server definition may name `rootMarkers` (such as `go.mod`, `go.work`, `pyproject.toml`). A file's server root is its nearest ancestor within the checkout that holds one, else the checkout root. A monorepo with several Go modules gets one server per module root. As built (step 3): markers are matched by name only, in directories from the file up to the checkout (never above it); the trust check, the shell environment and path mapping stay per checkout, so a file in a nested module still reports a checkout-relative path; a restart stops every server of a checkout; and when a file has several servers, one that cannot start is passed over (its reason is kept, and a refusal by the trust check reaches the reviewer as a notice) while the others answer.
- **Servers are data.** A definition is a command, arguments, a map from extension (or file name) to language id, `rootMarkers`, `initializationOptions`, `settings` (answers to `workspace/configuration`), extra environment, and where the program comes from. Beuve ships TypeScript and JavaScript (bundled, as now) and a definition for Go's `gopls`, which beuve does not bundle: it needs the reviewer's Go toolchain. Python and others are configuration or later built-ins.
- **Where the program comes from**, per server, as `source`:
  - `builtin`: shipped with beuve. Only the TypeScript pair.
  - `path`: an absolute command, or a name looked up on `PATH`. The default for everything but TypeScript.
  - `project`: a path relative to the checkout (for example `node_modules/.bin/…`), or for TypeScript, the project's own `tsserver`. This runs code that came with the reviewed branch.
- **`project` is the reviewer's choice and only theirs.** It takes effect only when the reviewer's own configuration asks for it, for the repositories they name. This is the same posture as the terminal (ADR 0095): beuve does not start repository code on opening a review, but the reviewer can decide to. ADR 0017's default (workspace binaries off, TypeScript pinned to beuve's own) stays for everything not opted in.
- **Finding programs: the reviewer's login-shell environment, as IDEs do.** A GUI app started from the Dock or Finder has a minimal `PATH`, so `gopls` from Homebrew, `go install`, `mise` or `asdf` would not be found. VS Code (`shellEnv.ts`) runs the user's shell as `-i -l -c`, reads the environment back as JSON from its own binary between random markers, gives up after 10 seconds (a setting, 1 to 120), does it once per process, and skips it when launched from a terminal and on Windows. Zed does the same from the home directory. Beuve does the same, as Zed does in two steps. First, once at startup, from the home directory, skipped when launched from a terminal, with a timeout: this is the base environment, and what the lookup of server commands uses before any checkout exists. If it fails or times out, beuve uses the process environment and shows an information notice. Second, per project (next bullet). Whatever environment results, only its `PATH` and the names a definition lists in `inheritEnv` (for Go, variables such as `GOPATH`) reach a server, on top of ADR 0017's allow-list. As built (step 2): the shell reads the environment back through the Node beuve already resolves (ADR 0083), not Electron's own binary; start-up files can tell they run for beuve from `BEUVE_RESOLVING_ENVIRONMENT=1`, as VS Code sets its own marker; the timeout is a fixed 10 seconds with no setting yet; and csh and tcsh get `-ic`.
- **Per project, as Zed does.** Zed also runs a login shell in the project's root and keeps that environment per project, for tasks, terminals and language servers, so per-directory tools (direnv, mise, asdf) take effect. Beuve does the same for a session: on the first server start for a session head's checkout, and again after Review › Restart Language Servers, it runs the same login shell with the checkout as its working directory, with the same flags and timeout, and caches the result for that checkout. That environment replaces the base for that checkout's servers. If it fails or times out, the servers get the base environment and the file shows an information notice.
- **Those tools' own trust decides what loads.** A shell that enters the checkout can load configuration that came with the reviewed branch (`.envrc`, `mise.toml`). ADR 0095 already settled this for the terminal: direnv and mise ask before trusting a new configuration (`direnv allow`, `mise trust`), that is the decision the reviewer makes, and beuve adds no prompt of its own. The same holds here. What each tool does with a configuration the reviewer has not allowed is its own behavior; the reviewer allows it in the terminal and restarts the servers, as ADR 0095 describes for installs. A hook with no trust step would run on entering the checkout, as it would in the reviewer's own terminal. The `env` of an override remains for a reviewer who wants to set a variable without a version manager.

### Trust

- **One decision point.** Every server start goes through one trust check. It takes the server definition, where its program comes from (`builtin`, `path` or `project`), where the definition came from (a built-in, the reviewer's file, or an override) and the repository, and answers allow, deny with a reason, or, later, ask. No code path starts a server without it.
- **A stub for now.** Version one answers from fixed rules: `builtin` and `path` are allowed; the per-checkout environment is allowed too, because direnv's and mise's own trust decides what it loads (see Servers), and it goes through the same check so beuve's own trust can gate it later; `project` is allowed only when the reviewer's own configuration asks for it for that repository, which counts as their consent; anything else, including a source kind the check does not know, is denied. It fails closed.
- **A denial is a normal outcome.** It is a typed result, not an exception, and the UI shows it as an information notice on the file ("the project's TypeScript server was not started: not trusted"). The denied path is built, rendered and tested from the first step, not added when a prompt exists.
- **Left for later:** how trust is granted or remembered (a prompt, a per-repository confirmation, a store). ADR 0096 removed the earlier trust grant, so a design starts from what the reviewer is asked and why, not from reviving it. Linters that load the repository's configuration (ESLint's config is code) are the first case that needs it.

### Configuration

- **One JSON file, `language-servers.json`, read from the places Ghostty reads its config.** Ghostty reads `$XDG_CONFIG_HOME/ghostty/` (`~/.config/ghostty/` when the variable is unset) on every platform and, on macOS, also `~/Library/Application Support/com.mitchellh.ghostty/`, loaded after the XDG files so it wins on conflict. Beuve reads `$XDG_CONFIG_HOME/beuve/language-servers.json` (`~/.config/beuve/` when unset) on every platform and `language-servers.json` in `userData` (on macOS, `~/Library/Application Support/beuve/`), loaded second so it wins. Neither is required. The files merge in that order: `servers` per id and per field, and `overrides` concatenated. Windows is not a target today (beuve ships for macOS and Linux, ADR 0048); when it is, `userData` applies there.
- **Hand-edited, read-only to beuve.** Beuve never rewrites these files, so ADR 0082's atomic-write rule does not apply to them. Settings gets a button that opens the file, creating an empty one in the XDG location if none exists. Review › Restart Language Servers re-reads them, as Ghostty reloads its config on a shortcut. The schema is strict (unknown keys and wrong types are errors, as for the model registry in ADR 0070). A missing or invalid file never blocks startup: beuve uses the built-ins and shows the error in Settings and the status bar.
- **`servers`** maps an id to a definition. A built-in id merges field by field over the built-in (so the reviewer can change `gopls`'s arguments or settings), `enabled: false` turns a server off, and a new id defines a custom server. As built (step 6): two fields combine instead of being replaced, `env` per variable and `inheritEnv` as a union, because the Go definition keeps safety settings in them and an override that set one variable would otherwise have dropped `GOTOOLCHAIN=local` and `GOPROXY=off`; a variable can still be given a new value.
- **`overrides`** is an ordered list of `{ match, servers }`. `match` is a path glob against the reviewer's own clone of the repository (`~` expands), so one entry can cover a directory of repositories and another a single repository, or a `remote` pattern such as `github.com/owner/*` for pull request sessions, which have no clone of the reviewer's. Entries apply in file order, later ones over earlier ones, merged per server id and per field over `servers`.
- **As built (step 4).** A server's entry takes `enabled`, `command`, `args`, `extensions` (extension to language id, such as `".go": "go"`), `rootMarkers`, `initializationOptions`, `settings`, `env`, `inheritEnv`, `source` (`path`, the default, or `project`; `builtin` is beuve's alone) and `diagnosticsQuietMs`. An override's `match` is an object, `{ "path": "<glob>" }` against the clone (a leading `~` expands) or `{ "remote": "<glob>" }` against `host/owner/repo` of a pull request, case-insensitively; `*` stays within a directory, `**` crosses them. Built-in servers come first in the order they are tried, then the config's new ones in the order they are first named. Anything the config says about a server, other than `enabled`, marks it as the reviewer's own, which is what lets `source: project` pass the trust check; a `project` program is a path relative to the checkout and must stay inside it after links are followed. A file that is invalid or unreadable is left out and named in a notice beside the diagnostics, and the other file and beuve's own servers are still used. Review › Restart Language Servers reads the files again, and Settings has a button that opens the file (creating an empty one in the XDG location when there is none). Later: `diagnostics: false` on a server hides its diagnostics while it keeps answering hover, definition, call hierarchy and symbols, which `enabled: false` cannot do because it removes the server; a server with it off is not asked for diagnostics and so is not started for them, and a file whose servers all have it off is `unavailable`. This is the same split VS Code's per-language validation switches make between what a server validates and what else it offers (from memory; the pages read for this had no example).
- **No configuration is read from the reviewed repository.** A `.beuve/language-servers.json` in a repository would let a pull request choose the programs beuve runs. A later ADR may read one as a suggestion that the reviewer approves; this one does not.

### Order of work

Each step is its own change and ADR amendment where it decides something:

1. Restore diagnostics in `src/internal/lsp`, with the push to the renderer, for TypeScript.
2. The login-shell environment (base and per checkout), and the trust check with its stub, including the denied notice.
3. The multi-server registry and `rootMarkers`.
4. The configuration file, its schema, overrides, both locations and the Settings entry.
5. Go: a `gopls` definition. Before writing it, run `gopls` against a sample module and record what it does: pull or push, which capabilities, which environment variables it needs, whether it touches the network (module or toolchain downloads) and how long it takes to settle on a cold checkout. Those facts decide its default `env`.
6. Python, as the first test of the configuration model with a server beuve does not bundle.

### What `gopls` was seen to do (step 5)

Run against sample modules through beuve's own multiplexer, with `gopls` v0.24.0 and Go 1.24.7 on Linux, on 2026-11-06. This is one version on one machine and small modules, not a survey; the findings decide the built-in definition's settings, and should be re-checked when `gopls` changes.

- **Protocol.** Push diagnostics. Compile errors carry `source: compiler` and codes such as `UnusedImport`, `UnusedVar`, `IncompatibleAssign`, `BrokenImport`; analyzer findings carry the analyzer as source (`printf`, `rangeint`) and code `default`. A cold first file settled in about 2 s, later files in about 0.6 s.
- **Analyzers come second.** They arrive after the type check. With the 500 ms quiet period beuve settled first and called a file with a `printf` problem clean; with 3 s both findings arrived. The Go definition therefore waits 3 s (`diagnosticsQuietMs` can change it), which makes a Go file take at least that long to settle. While a package has compile errors, no analyzer findings were seen.
- **Roots.** A `go.mod` marks a module; a repository with a nested module got a second server rooted there, and each reported its own files.
- **Mutation and network.** With `GOFLAGS=-mod=mod`, `go` added a `require` to the checkout's `go.mod`, created a `go.sum`, and downloaded the module. With nothing set, it did none of that, and a missing dependency was an ordinary `BrokenImport` error.
- **A toolchain line is a download.** A `toolchain go1.99.0` line in the reviewed `go.mod` made `go` request that toolchain's zip from the proxy, which is a program fetched on the branch's say-so. `GOTOOLCHAIN=local` made no request and `gopls` still reported normally.
- **A `go.mod` newer than the installed Go.** `go 1.99` with `GOTOOLCHAIN=local` made `gopls` fail to initialise (it reports a warning on line 1) and never settle, so beuve waits out its deadline (20 s) and marks the answer incomplete.
- **Offline.** With `GOPROXY=off`, a dependency missing from the module cache is a `BrokenImport` error with no network request; with it in the cache, the file is clean. That fits ADR 0095: the reviewer installs dependencies in the terminal, then restarts the servers.

So the built-in definition sets `GOTOOLCHAIN=local` and `GOPROXY=off`, passes on `GOPATH`, `GOMODCACHE`, `GOCACHE`, `GOROOT` and the `XDG_*` locations, and does not pass on `GOFLAGS`. It does not force `GOFLAGS=-mod=readonly`, because that would ignore a `vendor` directory. A `GOFLAGS` set with `go env -w` lives in Go's own environment file, which is not turned off, so a reviewer who set `-mod=mod` there would still see it; they can set `GOFLAGS` in the config. Not done: `go.work` as a root marker, and the `go.mod` newer than the installed Go case, which settles only at the deadline.

### What Pyright and Ruff were seen to do (step 6)

Python is the first test of the configuration model with servers beuve does not bundle, so there is no built-in definition: Pyright (`pyright-langserver --stdio`, from npm) and Ruff (`ruff server`, from pip) were defined only in a `language-servers.json`, and run through the main services against a sample repository on 2026-11-06 (Pyright 1.1.414, Ruff 0.17.4, Linux). One run of small projects, not a survey.

- **Several servers per file works as designed.** Both ran for every `.py` file, and their diagnostics came back together, each tagged with its server: Pyright's type errors (`reportAssignmentType`, `reportUndefinedVariable`) and Ruff's lint (`F401`, `F841`, `F821`, `I001`).
- **Roots.** `pyproject.toml` as a root marker gave a nested project its own pair of servers, so a checkout with one nested project ran four servers. Idle shutdown (ADR 0017) bounds that.
- **Settling.** Both answered within about a second at the default 500 ms quiet period; 2.5 s gave the same findings. No per-server tuning was needed.
- **Nothing special in the environment.** The programs were found by absolute path here; by name they are found on the login-shell `PATH`, as for `gopls`.
- **Messages.** Ruff puts a `help:` line in the message after the first, and Pyright sends "not accessed" hints for unused names; both are shown as given.

What the run showed about the model itself was the merge rule above. The documentation is `docs/language-servers.md`, with a complete example in `docs/examples/language-servers.json`, which a test parses and resolves so it cannot go stale.

## Consequences

- Reviewers see type and lint errors where the code is, for any ecosystem with an LSP server, with no per-ecosystem logic in beuve beyond a default definition for each language we choose to ship.
- Beuve gains a user-edited config file (in two possible places) and a path-matching rule to maintain, and the rule that repository content never defines a program to run. The cost is that a repository cannot carry its own server setup: the reviewer writes it once in their own file.
- `source: project` makes it possible to use the project's own TypeScript, so diagnostics match the project, after the reviewer installs dependencies and opts in. Until then TypeScript diagnostics come from beuve's version and may differ from the project's.
- Server commands are found through the reviewer's login-shell `PATH`, so Dock and Finder launches work like an IDE's. This puts back the login-shell capture ADR 0095 removed for installs, for a different purpose: once at startup in the home directory, and once per checkout when its servers first start, each with a timeout. It runs the reviewer's shell start-up files, as their terminals already do, and in a checkout it runs whatever direnv, mise or a similar tool will load there under their own trust rules. A definition can still name an absolute command.
- Trust is a stubbed seam with the denied path already built and tested. Granting trust is not designed yet, and `project` sources are limited to what the reviewer's own file opts into until it is.
- A checkout whose environment is not yet allowed gets the base environment, so a Go or Node server may start with the wrong toolchain until the reviewer allows it and restarts. The information notice should say so.
- Diagnostics exist at the session head only. A reviewer reading an old commit in a sheet sees the information icon and no markers.
- A server per module root and several servers per file mean more processes. The idle shutdown (ADR 0017) bounds that.

## Decisions on the open questions

The first draft left four questions open. The reviewer decided them on 2026-11-06:

1. **Finding programs:** follow what IDEs do, a login-shell environment (see Servers). Per project too, as Zed does: the reviewer pointed out that direnv and mise have their own trust mechanisms, and ADR 0095 already relies on them. The first draft of this amendment left per-project out, and that was reversed.
2. **Config location:** follow Ghostty, XDG on every platform plus the platform's own directory on macOS (see Configuration).
3. **Sheets at older commits:** no diagnostics; an information icon says so (see What the reviewer sees).
4. **Trust:** not designed yet. Build a single trust check with a stub that fails closed, so every code path exists from the start (see Trust).
