# 0112. Remote-branch sessions: reviewing a GitHub branch that has no pull request

- Status: Accepted
- Date: 2026-11-06

## Context

Cloud agents push `claude/*` branches and often never open a pull request, or open one late. Today a reviewer can open a local session on `origin/claude/foo`, but beuve never fetches for it (ADR 0037 fetches only pull requests), so the head moves only when the user runs `git fetch`, and nothing notices the pull request once it exists. The session model (ADR 0009) has two kinds, and its review state, checkpoints, file marks and URA items hang off the session id, so a branch reviewed before its pull request existed should become that pull request's session rather than a second one.

## Decision

- **Source kind `remote-branch`** (`SessionSource`): `repoPath`, `baseRef`, `forge`, `host`, `owner`, `repo`, `branch`. `forge` names the adapter that fetches and polls it; it is `'github'` only, and the column CHECK lists it. The session domain and the git layer know nothing of GitHub: a GitLab or plain-git remote is a new `forge` value plus an adapter in main, not a new kind. Columns `forge` and `branch` are null on other kinds; `host`, `owner`, `repo` are shared with pull request rows. A partial unique index `(repo_path, forge, host, owner, repo, branch) WHERE kind = 'remote-branch'` makes opening idempotent through `findSessionBySource`. The migration is squashed into `session-0001-initial` (no release yet, ADR 0006 amendment).
- **Refs**: the head is fetched into `refs/beuve/branch/<key>/head` and the repository's default branch into `refs/beuve/branch/<key>/base`, where `<key>` is the first 24 hex digits of SHA-256 over lowercase `host/owner/repo` and the branch name. A hash, because branch names nest (`a` and `a/b` can't both be refs) and repository names may start with a dot. `baseRef` is that constant base ref, so a changed default branch keeps the session. Fetching is ADR 0037's `fetchRefs` (`--refmap=`, destinations only under `refs/beuve/`) through the clone's remote for the repository; the user's remote-tracking refs never move. Fetch-and-verify: the fetched head must equal the SHA GitHub reported; one mismatch asks GitHub again, a second is `head-mismatch`. Branch names are limited to the conservative ref subset `buildPullRequestFetch` already uses. The diff runs from ADR 0054's stack-aware fork point like every other session.
- **Clone policy**: ADR 0037's, unchanged and shared: never clone, use `repoPath` or `githubClonePaths`, require a remote naming `host/owner/repo`, else `needs-local-clone`.
- **Opening**: `github:open-branch { ref, repoPath?, requestId? }` mirrors `github:open-pr`. `ref` is a tree URL (`https://<host>/<owner>/<repo>/tree/<branch>`, everything after `tree/` is the branch, so a URL into a directory of a branch is not supported) or `[host/]owner/repo:branch`. It costs `GET /repos/{o}/{r}` (default branch and canonical names), `GET /repos/{o}/{r}/branches/{branch}` and one fetch. When the clone has no session for the branch yet and the branch already has an open pull request, the pull request is opened instead (`github:open-pr`'s path; the answer has no `branch`), so a branch never starts a second session beside its pull request's. Metadata goes in the github domain's `github_branches` table, keyed by `(host, owner, repo, branch)` like `github_pull_requests`: default branch, last head, `present | gone`, the open pull request number when one exists, fetch time. No ETags or tokens.
- **Polling** (ADR 0038's poller, still one session at a time): a remote-branch session polls `GET …/branches/{branch}` with its ETag (a 304 is free). A new head is fetched, verified and stored with `advanceHead` / `onHeadMoved`, as for pull requests. **Pull request detection**: `GET /repos/{o}/{r}/pulls?state=open&head={owner}:{branch}` with its own ETag, on open, whenever the branch answer changed, and otherwise every fifth poll (about five minutes while focused). Only pull requests in the same repository are found; a pull request from a fork into another repository is not. With several, the lowest number wins.
- **Promotion in place**: a found pull request is fetched and verified as on `github:open-pr` (`refs/beuve/pr/<n>/…`), its metadata stored, and `promoteSession` rewrites the row in one `UPDATE … WHERE kind = 'remote-branch'`: kind `github-pull-request`, `pr_number`, `base_ref` `refs/beuve/pr/<n>/base`, `forge` and `branch` cleared. The id stays, so checkpoints, file marks, URA items, chat and review edits stay. A moved head then goes through `moveSessionHead`. **Collision**: if a pull request session for that clone and pull request already exists, nothing is merged or promoted; the branch session records the pull request number, keeps polling its branch, and the UI links to the existing session. Merging two sessions' histories across five domains' tables is not worth it for a case the reviewer creates by opening both.
- **Branch gone**: a 404 on the branch marks it `gone`; the last head and everything reviewed stay, and the poller stops scheduling that session. Selecting the session again (or opening the branch again) polls once; a branch that answers again is `present` and polling resumes.
- **Events**: `github:branch-updated { sessionId, branch, headMoved, promoted }` whenever the head, the `present | gone` state or the pull request changed (an answered poll alone is not a change). On `promoted` the renderer reloads the session, which now loads as a pull request; the poller polls it as one at once, so `github:pr-updated` and CI follow. `github:get-branch { sessionId }` returns the stored branch view and makes the session the polled one, like `github:get-pr`. `session:list` adds `remoteBranch { state, defaultBranch }`.
- **Feedback without a pull request**: nothing is posted; the posting dock only exists for pull request sessions. Review output goes through the existing export and copy paths (ADR 0023). If the head commit has a `Claude-Session: <https URL>` trailer (in its last paragraph, every line a trailer), the branch view carries it and the status bar beside the branch's state links to it ("Agent session") through `shell:open-url`. The commit is read with a new typed operation, `readCommitMessage`, on the warm `cat-file --batch-command` reader (ADR 0087).
- **Entry points**: `beuve://open?url=https://<host>/<owner>/<repo>/tree/<branch>` is a second link target beside pull requests (`githubLinkFrom`, which replaces `pullRequestLinkFrom`), with the same consent prompt ("Follow branch host/owner/repo:branch?") and a `link:open-branch { ref }` push. The open panel, its "Pull request or branch…" step and the palette take a tree URL or `[host/]owner/repo:branch` as well as a pull request; the renderer sends a branch to `github:open-branch`. The status bar shows "Following <branch>", "<branch> is gone from GitHub" or "PR #n has its own review"; the session list and palette mark a gone branch.

## Consequences

- A cloud agent's branch can be reviewed as it is pushed and keeps its review when the pull request appears. An idle branch session costs one conditional request a minute and one more every five.
- `refs/beuve/branch/*` names are opaque hashes; `git for-each-ref refs/beuve/branch` shows them but not which branch they are.
- A fork's pull request is not detected, and the `Claude-Session` link disappears once the session is a pull request (the PR view does not read trailers yet). A local session on a remote-tracking branch is still a local session; the local-branch picker does not offer to follow it instead. The colliding-branch UI names the other session but has no button to switch to it. All are left for later.
- A 404 for a branch in a private repository the token can't see reads as `gone` too.
- The review queue can reuse `github:open-branch` to open a candidate branch, and `github_branches` to show which branches have been opened.
