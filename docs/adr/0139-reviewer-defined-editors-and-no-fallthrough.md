# 0139. Editors the reviewer defines, Gram built in, and no stand-in editor

- Status: Accepted; amends [0033](0033-open-in-editor.md) (registry, preference, which editor opens) and [0068](0068-native-menus-chorded-keymap-and-a-settings-window.md) (Open With, Settings)
- Date: 2026-11-18

## Context

Open Review Edits (ADR 0088) started Cursor for a reviewer who has neither Cursor nor Zed. ADR 0033's choice rule was "the preferred editor if installed, else the first installed one", so an unset preference, or a preferred editor that wasn't found, quietly became whatever detection turned up first; a leftover `Cursor.app` or a stale `cursor` shim on `PATH` was enough. The registry was three hard-coded entries (Zed, VS Code, Cursor), so the reviewer could neither add the editor they use nor take one away. They asked for Gram, a fork of Zed, as their default, and for editors to be configurable, preferring a JSON-only option, as VS Code has for some settings, over a richer UI.

Gram was checked against its source (codeberg.org/GramEditor/gram, `main`, read on 2026-11-18): the macOS bundle is `Gram.app` (`package.metadata.bundle-stable`, identifier `app.liten.Gram`) with its CLI at `Contents/MacOS/cli` (`script/bundle-mac`); the CLI is named `gram`, and the Linux install script links it as `~/.local/bin/gram`; the CLI takes `path:line:column` as Zed's does; and the app registers the `gram` URL scheme and opens `gram://file<path>` (`osx_url_schemes`, `open_listener.rs`).

## Decision

### Editors are data the reviewer can extend

- **Built-ins**: Zed, Gram, VS Code and Cursor, in that order (the order Settings and the menu list them; it no longer decides anything). Gram is found as `gram` on `PATH`, `/Applications/Gram.app/Contents/MacOS/cli`, `~/Applications/Gram.app/Contents/MacOS/cli`, `/usr/local/bin/gram`, `/opt/homebrew/bin/gram` and `~/.local/bin/gram`, and is invoked as `gram path:line:column`; with only the app bundle, `gram://file/<path>:<line>:<column>`, which `isEditorUrl` now allows beside `zed:`, `vscode:` and `cursor:`.
- **Arguments are a template**, for built-ins too: one array entry per argument, with `{file}`, `{line}` and `{column}` filled in. Zed and Gram use `["{file}:{line}:{column}"]`, VS Code and Cursor `["--goto", "{file}:{line}:{column}"]`. Filling in never splits or re-reads an argument, and processes still start without a shell (ADR 0033).
- **`editors` in `settings.json`** is a map from editor id (lowercase letters, digits and dashes, starting with a letter) to an entry with `name`, `command`, `args` and `enabled`, all optional. An entry for a built-in id changes what it names: `enabled: false` removes it, `name` and `args` replace its own, and `command` replaces every place beuve looks for it, the macOS app and URL fallback included, so a reviewer who points beuve at a program gets that program or a clear failure. A new id adds an editor and needs `command`; `name` defaults to the id and `args` to `["{file}"]`. `command` is an absolute path, a path under `~/`, or a bare name looked up on `PATH`; a relative path with a slash is refused. An editor of the reviewer's own has no URL form: a reviewer on macOS names the CLI inside the app instead. That keeps `shell.openExternal` limited to the four known schemes.
- **Validation** is strict per entry (zod, as for `language-servers.json`, ADR 0111): unknown keys, wrong types, a placeholder other than the three, or `args` without `{file}` leave that entry out. One sentence per bad entry, naming its path (`editors.helix.args.0: …`), goes to the log once per change and to `EditorSettingsView.problems`, which Settings and `/editor` show. The other entries and the built-ins still work.
- **Read on use.** The file is read on every `editor:open`, `editor:get-settings` and review-edits launch, so a hand edit takes effect without a restart. beuve never writes `editors`; it keeps the key, like any other, when it rewrites the file for `preferredEditor` and the other preferences.
- **A malformed `settings.json` is never replaced.** Reading it as `{}` stays (a bad file never blocks startup), but `updateSettingsFile` now refuses to write over a file that exists and is not a JSON object, so a typo in a hand edit can't be wiped out by the next preference change. The change that triggered the write fails with a message naming the file.

### Which editor opens: the reviewer's, never a stand-in

- **A chosen editor is the only one.** When `preferredEditor` names an editor that is not found, Open in Editor and Open Review Edits fail with `editor-unavailable` ("Gram, your chosen editor, was not found. Install it, set its "command" in settings.json, or choose another in Settings › Editors."). When it names an id `settings.json` no longer defines, the same failure says so. Nothing else is started.
- **No choice**: exactly one installed editor is used. Several give `editor-not-chosen` with their names; none gives `no-editor-found`. In both cases the reviewer is asked to choose rather than beuve guessing by registry order. An editor is only ever started because the reviewer chose it, or because it is the only one there is.
- The status bar notice for these three failures has an **Editor Settings…** button. `EditorSettingsView.current` is the editor that would open now by these rules, for Settings and `/editor`.

### Open With, `/editor` and Settings

- **One catalog command expands into the list.** Per-editor catalog commands can't describe editors that exist only in a reviewer's file, so the three `editor-*` commands are replaced by `open-with-editor` with `expands: 'editors'` (ADR 0068's catalog stays the single list of commands). `menuTemplateFrom` turns it into one radio item per known editor, id `open-with-editor:<editor id>`, labeled with the editor's name and "(Not Found)" when it is missing, or one disabled "No Editors Found". Choosing one sends `menu:run { id: 'open-with-editor', argument: <editor id> }`, and the main window stores the choice as before. Such a command has no keys, so ADR 0068's "every shortcut has a menu item" is unaffected; its palette entry, Choose Editor…, prefills `/editor `.
- **Main owns the list and the check.** `EditorServices.onChanged` reports each settings read that differs from the last; `startApp` turns it into `AppMenus.setEditors`, which rebuilds every menu when the list changed and otherwise only moves the radio check to `preferredEditor`. Main reads the settings at startup and whenever a main window gains focus, which is how a hand edit reaches the menu. The renderer no longer reports editor checks in `menu:set-state`.
- **Editor Settings…** (`editor-settings`, Review › Open With, after a separator; a main-process command) opens the Settings window.
- **`/editor <id>`** takes any well-formed id (`code` still means `vscode`); main answers an unknown one with the ids it knows. `/editor` alone prints the choice, what happens without one, every editor by id with "not found" where it applies, and the configuration's problems.
- **Settings › Editors** lists every editor with a radio button, its name, a Custom badge when `settings.json` defines or changes it, and where it was found ("Command: <path>" or "App, opened by URL: <path>", through `pathText` with the raw path as the title) or "Not found"; the problems; a note on what opens without a choice or why the choice can't open; and **Open settings.json**, a new Settings-only channel `editor:open-settings-file` that creates `{}` (0600) when the file is missing, never rewrites one that exists, and opens it with `shell.openPath`. The window reads the editors again when it regains focus. This is the one preference with a menu toggle that Settings also sets (amending ADR 0068's 2026-11-06 rule): the menu can show neither where an editor was found nor what is wrong with the file, and the place that explains a choice should also let the reviewer make it.

## Consequences

The reviewer can use any editor that opens a file from a command line, including a terminal editor wrapped in a terminal command (`"command": "kitty", "args": ["hx", "{file}:{line}:{column}"]`), and can hide built-ins they don't want offered. A reviewer with several editors and no choice now gets a notice instead of an editor on first use; that is one extra step, accepted so beuve never opens a program the reviewer didn't pick. A missing chosen editor is a failure rather than a silent substitute. Adding a built-in is a registry entry with an argument template; a new URL scheme still needs `isEditorUrl`. The menu is rebuilt when the editors change, which Electron allows at any time; only the Open With list depends on it. Editors are global, not per repository, and Windows is still not supported. The documentation for the format is `docs/editors.md`, with an example in `docs/examples/editors-settings.json` that a test parses.

## Amendment (2026-11-18): the editor is a setting only

The reviewer asked that the default editor be set only in Settings, not from the menu, so it is now an ordinary setting with no menu toggle, which ADR 0068's 2026-11-06 rule already permits; the exception recorded above under "Open With, `/editor` and Settings" no longer exists.

- **No Open With list.** `open-with-editor`, the catalog's `expands` field, `menuTemplateFrom`'s editor entries, `MenuRunView.argument`, `AppMenus.setEditors`, `EditorServices.onChanged` and the menu refresh on window focus are removed. Main no longer reads the editors to build menus.
- **Editor Settings…** stays, now directly in Review beside Open in Editor (the Open With submenu would have held only it), and opens the Settings window, whose Editors section is its first.
- **No `/editor`.** Chat commands no longer set preferences (ADR 0139, chat commands act on the conversation), so `/editor` is gone with the others; typing it says the editor is chosen in Settings › Editors (Review › Editor Settings…). There is no List Editors command: Settings › Editors lists the editors, the choice and the configuration's problems.
- **`editor:set-preferred` is Settings-only**: it moves to `settingsOnlyInvokeChannels`, so main refuses it from the main window and sheets, and only Settings › Editors stores `preferredEditor`. The failure messages point to Settings › Editors alone.
