# 0113. A review queue: everything waiting on the signed-in GitHub user, in one list

- Status: Accepted
- Date: 2026-11-06

## Context

beuve opens one change at a time: a pull request someone pasted, a branch an agent pushed (ADR 0112), a local range. Finding out what to open is still done on GitHub: the review-requests page, one's own pull requests, and the branches cloud agents left without a pull request, which GitHub lists nowhere at all. None of those know what beuve knows: which of them were already opened here, how far the review got, and whether new commits arrived since the last checkpoint (ADR 0009, 0064). A queue that merges the two answers "what should I look at next" without leaving the app, and is the natural home screen when no session is open.

## Decision

- **Sources** (GitHub only today; items carry `forge: 'github'` like ADR 0112's sessions, so another forge is another adapter in main, not another item kind):
  1. Review requests: `GET /search/issues?q=is:open is:pr archived:false review-requested:@me` (includes team requests), and the same with `user-review-requested:@me` to tell direct requests from team ones (`request: 'direct' | 'team'`). New operation `searchPullRequests` (paged, at most 2 pages of 100, truncation reported).
  2. The viewer's own open pull requests: `… author:@me`.
  3. Agent branches without a pull request, in every repository in `githubClonePaths` or with a beuve session on that host: `GET /repos/{o}/{r}/git/matching-refs/heads/{prefix}` per configured prefix (default `claude/`), conditional on its ETag (`listMatchingBranches`). Branches with an open pull request are dropped using one `GET /repos/{o}/{r}/pulls?state=open&per_page=100` per repository, conditional (`listOpenPullRequests`), rather than `findBranchPullRequest` per branch: one request per repository instead of one per branch. A branch whose `GET /repos/{o}/{r}/compare/{default}...{head}` says `ahead_by == 0` (merged, or identical to the default branch) is dropped; the compare is needed for its size anyway.
  4. Local review state from beuve's sessions, matched by `host/owner/repo#number` or `host/owner/repo:branch` (case-insensitive): `none` (never opened), `opened` (no checkpoint, no file marks), `partial` (file marks on the session head, no checkpoint), `reviewed` (the last checkpoint's head is the item's current head), `new-commits` (a checkpoint, and the head moved since). The item's head is GitHub's (from the pull request or the branch tip), so new commits show before the session is opened again.
- **Per item**: kind, `host/owner/repo`, number or branch, title (a branch's is its head commit's subject), author (a branch's is its head commit's author), draft, created and updated times, size (`additions`, `deletions`, `changedFiles` from `GET …/pulls/{n}` for pull requests, summed from the compare for branches), CI (`getCiStatus` on the head), attention (`attentionFrom` over `…/reviews` and `…/requested_reviewers`; a branch reads as the viewer's turn, "an agent branch has no pull request yet"), why it is in the queue (`requested`, `authored`, `branch`), the stack it belongs to, the matching session and, for branches, the head commit's `Claude-Session` link (the compare already carries the message). **Waiting since** is `updated_at`: the timeline operation of ADR 0110 does not read `review_requested` events, and reading `…/issues/{n}/events` per pull request is a request per item for a better guess. Documented as an approximation.
- **Stacks** come from data already fetched: within one repository, a pull request whose base branch is another queued pull request's head branch is its child. No extra requests; a stack whose middle is not in the queue shows as two stacks.
- **Caching** (in memory, per run): a pull request's details, reviews and requested reviewers are re-read only when its search `updated_at` changed (a push, review, request or comment changes it); CI is asked each refresh with its ETags, which mostly answer 304 at no rate-limit cost; a branch's compare is keyed by `(default branch, head SHA)`; the repository, branch listings and open-pull-request lists are conditional on their ETags. A refresh where nothing changed therefore costs the three searches and conditional requests.
- **Budget per refresh and host**: 3 search requests (6 at most with a second page), plus per repository 1–2 + one per prefix conditional requests, plus 2 conditional CI requests per item and 3 full requests per changed pull request (one compare per new branch head). Search has its own limit (30 a minute); search rounds are at least 20 s apart, so a forced refresh inside that floor returns the current snapshot. Item requests run four at a time.
- **Pace**: a queue poller in main, separate from the session poller (ADR 0038). It starts when the renderer first asks for the queue, refreshes every 5 minutes while a window has focus and five times less often otherwise, and on focus when the last refresh is older than the interval. A failure doubles the delay up to 30 minutes; a rate limit waits until its `resetAt` (at least 1 minute, at most 30). Every request takes the poller's abort signal, which disposing aborts.
- **Partial failures**: a search, repository or item that fails keeps its last good items and is listed as a `problem` (what failed and why) beside the items; the list is never blanked by one failed source. A host without a credential is a problem too.
- **Contract**: `queue:get` (the snapshot, refreshing first if it is stale or there is none), `queue:refresh` (refresh now, within the search floor), and the push `queue:updated` with the whole snapshot (`items`, `problems`, `refreshedAt`, `isRefreshing`). The snapshot is small (one row per item), so pushing it whole beats patching.
- **Sorting, grouping and filtering** happen in the renderer on the snapshot, in pure table-tested functions (`src/ui`), so changing them is instant and costs no requests. Sorts: your turn first (default), waiting longest, oldest, recently updated, smallest, largest, stack order (each stack bottom-up, stacks kept together), new since your review; ties break on `host/owner/repo`, then number or branch. Groups: none (default), repository, stack, turn, kind, local review state. Filters: kind, repository, author, direct or team request, drafts, CI, turn, local state, and free text over title, repository, branch and author. **Default filter**: everything except the viewer's own pull requests that are not their turn ("waiting on others"); one toggle shows those too. The choices are display preferences (ADR 0042) in `settings.json` under `reviewQueue`; the free text is not kept.
- **Settings**: the branch prefixes are `reviewQueueBranchPrefixes` in `settings.json`, edited in the Settings window as a comma-separated list (empty turns branches off). A prefix is a ref path prefix (`claude/`), at most 8.
- **UI**: `Review Queue` (File menu, under Open; ⇧⌘R / Ctrl+Shift+R; in the palette) shows the queue. With no session open the home screen shows the queue above the Open panel; with one open, the command shows it in a wide dialog. Rows show a kind icon, repository and number or branch (through `revealFormatControls`), title, author, size, CI, the turn chip with its reasons as the tooltip, the local review state badge and the age; the header has a sort menu (ADR 0107), a group menu, a filter menu and "Updated N min ago" with a refresh button; problems show as a quiet line under the header. Up/Down move, Enter opens through `GithubController.open` (a pull request by `host/owner/repo#n`, a branch by `host/owner/repo:branch`), whose `needs-local-clone` answer shows the Open dialog's pull step for that ref. Rows use `ActionDelegation`.

## Consequences

- Opening beuve shows what is waiting, with how far each review got, without a trip to GitHub. A quiet queue costs three searches and some 304s every five minutes.
- Only branches of repositories beuve already knows are listed; a branch in a repository never opened here does not appear. Forks' pull requests from the viewer's own branches show through search like any other.
- "Waiting since" is the last update, not the time the review was requested; a comment resets it.
- A team request whose team the viewer left still shows until GitHub's search stops returning it. Search results lag behind writes by up to a minute, as on GitHub's own pages.
- Caches live for the run; the first refresh after launch re-reads every item's details once.
