# 0132. Chat answers propose review notes the reviewer stages

- Status: Accepted; amends [0055](0055-review-folded-into-chat-with-verification.md) (the `chat-answer` origin) and [0031](0031-read-only-qa-chat.md) (the question system prompt)
- Date: 2026-11-10

## Context

A reviewer often asks the chat "what would you comment on here?" and then copies Claude's answer into notes by hand. `/review` findings are already stageable one at a time (`ura:stage-review-finding`, ADR 0055), and a whole answer can be staged as one comment (ADR 0032), but an ordinary answer cannot hand over several notes, each on its own lines. There is no MCP server any more (ADR 0106), so Claude cannot call a tool to stage a note, and it must not: what goes into the review is the reviewer's decision. The proposals have to come through the answer itself, as text main can check.

## Decision

- **The question system prompt offers it.** When main asks a question (not `/review`, `/summarize` or `/compact`), `ChatQuestion.proposals` carries `{ labels, maxProposals: 10 }` and the system prompt tells the model it may propose inline notes when the reviewer asks for them or one would clearly help, that it never stages anything, and how to write one. The labels are the URA's (the Conventional Comments labels and `smell`, ADR 0131: `uraSeverities`, passed by main typed as `UraSeverityView[]`), listed in the prompt from that array, so a change to the note labels changes the prompt with no other edit. The chat domain stores a label as text and never names the list. The prompt tells the model to write `(blocking)` only when the reviewer asked for blocking notes or the problem clearly must be fixed before merging.
- **A strict block syntax in the Markdown.** A proposal is a block whose first line is `:::note <label> [(blocking)] [[path:start-end]] <optional title>` and whose last line is `:::`, both at the start of a line and outside fenced code; the lines between are the body (fenced code in the body may contain a `:::` line). The anchor is the citation syntax (ADR 0031), parsed by `parseCitations`, so a path may hold spaces or colons. The decoration is written as Conventional Comments writes it (`:::note issue (blocking) [[src/a.ts:12]] Empty input`); without it, or with `(non-blocking)`, the note does not block, and any other parenthesized decoration makes the block `malformed`. `parseNoteProposals` splits the answer into text and blocks; a block whose first line does not parse is dropped as `malformed`, and one that never closes is `malformed` with its lines kept as text. A `:::note` anywhere else is ordinary text.
- **Validated like findings when the answer completes.** `validateNoteProposals` checks each block: a label that was offered (`unknown-label`), head-side lines of a text file of the diff touching a hunk, narrowed to the hunks (`unknown-file`, `outside-diff`; the same check as findings, now `DiffHunkIndex`, which `validateFindings` uses too), a title made one line of at most 200 characters, a title or a body (`malformed`), no repeat of the same lines and title (`duplicate`), and at most ten (`over-limit`). Order is the answer's; nothing is ranked. Citations are checked per text piece and listed once across the answer.
- **Stored as parts of the answer, no chat migration.** A kept proposal is a `proposal` part `{ proposal: n, note: { path, startLine, endLine, label, blocking, title, body } }` in its place among the text parts (n counts proposals, 0-based); a dropped one is a `dropped-proposal` part with its reason, where the block was. `answerPartsFrom`'s ending for an answer is now its pieces (`{ kind: 'answer', pieces }`, replacing `text`); the first text piece keeps the streamed text's part id. `chatMessageFromRow` checks that proposals are numbered 0, 1, 2, … and only appear in a done answer. For later prompts `chatTextFrom` writes a proposal back as its block, so the model sees what it proposed. While the answer streams, the raw block shows as text, as raw citations do.
- **The transcript shows each proposal as a card.** In place in the answer: the label with its emoji (`uraSeverityEmoji`, which covers every label), and for a blocking note 🛑 (`uraBlockingEmoji`) and "(blocking)" in the danger color, as the dock shows it, then "Proposed note", the title and body as the safe Markdown subset (citations stay text), a citation pill and a Stage button, which reads "Staged" while the item is staged. A dropped proposal is one muted line saying why. Staging the whole answer leaves the proposals out (they are staged one by one). A stored label that is no longer a note label reads as a `dropped-proposal` of `unknown-label` (`chatPartViewFrom`).
- **Staging is the reviewer's click, read from the stored answer.** `ura:stage-note-proposal { messageId, proposal, severity? }`: main finds the `proposal` part in the stored answer (the renderer never supplies its text), and stages it on its lines at the answer's head with the proposed label, unless `severity` replaces it, blocking when the note was written `(blocking)`, and origin `{ kind: 'chat-answer', messageId, proposal }`. Like findings, it is idempotent per (message, proposal): `ura_items.chat_proposal` has a partial unique index, and staging again returns the item, restaging a withdrawn one. A blocking proposal blocks Approve once staged (ADR 0131); the card showed 🛑 and "(blocking)" before the click, unlike `/review` findings, which never block on their own. The URA origin gains `proposal?`, never set with `finding`; the agent XML export carries it as a `proposal` attribute. The column is in `ura-0001-initial`: migrations are still squashed until the first tagged release (ADR 0006 amendment), so a database made before this change must be recreated.
- **No "Edit then stage".** Staging is one click, and a staged note is edited where it is shown (ADR 0129), which covers changing it before export without a second composer path.

## Consequences

An answer can carry several ready-made notes, each checked against the diff, and the reviewer stages the ones they agree with; nothing reaches the dock without that click. Proposals cost no extra model call and no new channel to the model: they are text the answer already returns, parsed once. The model can still write a block wrongly; those are dropped and said so in place rather than silently lost.

The syntax is a convention the model may ignore or get wrong, and the prompt grows by a dozen lines for every question, used or not. A label change changes the offered list mechanically; a stored proposal whose label is gone reads as dropped. Whether a note blocks is the model's reading until the reviewer stages it, which is why the card shows it first. Proposals are anchored only to lines in the diff, like findings; a note on a whole file or on the change is not proposable.
