# 0049. CI matrix, versioning, GitHub Releases and a Homebrew cask in this repository

- Status: Accepted, Gatekeeper decision amended 2026-10-29
- Date: 2026-10-29

## Context

beuve targets macOS, but CI ran only on Ubuntu, so macOS-only failures surfaced at release time, if ever. Releases (ADR 0048) made a draft with GitHub's generated notes from a `v*` tag, with nothing checking that the tag matched `package.json`. There was no way to `brew install` the app. The author doesn't want the official `homebrew/cask`, and the build is ad-hoc signed and not notarized.

## Decision

- **CI matrix.** `ci.yml` runs `npm run check` on `ubuntu-latest` and `macos-latest` (Apple silicon, the architecture beuve ships), `fail-fast: false`, Node 24, npm cache, one run per ref (a newer push cancels the older). Tests are fixed to be portable rather than skipped. The first macOS run found one failure: the fake `claude` CLI listed `__CF_USER_TEXT_ENCODING`, which macOS adds to every spawned process's environment, in the env keys a test pins exactly. The fake now leaves that key out.
- **Versioning.** `package.json` is the single source of truth. `npm version patch|minor|major|prerelease` bumps it, commits and tags `v<version>` locally, and `git push --follow-tags` publishes. `release.yml` fails when the tag differs from `package.json`. A manual run without a tag builds `<version>-dev.<short sha>` (through `BEUVE_BUILD_VERSION`, which `scripts/dist-mac.ts` passes to electron-builder as `extraMetadata.version`) and uploads the artifact without a release.
- **Release.** On a tag the macOS job builds the ad-hoc arm64 dmg and zip and `SHA256SUMS`; an Ubuntu job publishes a non-draft GitHub Release with `gh release create` and `GITHUB_TOKEN` (`contents: write`), marked prerelease when the version has a suffix. **Release notes come from a small script** (`scripts/release-notes.ts`, logic in `src/pkg/release/`), not `--generate-notes`: work lands as conventional commits directly on `main`, and GitHub's generated notes list merged pull requests, which would be empty. The script groups feat, fix, perf, refactor, docs and other, skips cask bump commits, and appends the compare link and install instructions. It needs no dependency.
- **Homebrew: a cask in this repository, `Casks/beuve.rb`.** A GUI app is a cask, and a tap is a git repository of casks. A tap needs no separate repository: `brew tap bdchauvette/beuve https://github.com/bdchauvette/beuve` (the explicit-URL form is for repositories not named `homebrew-*`) then `brew install --cask beuve`. The cost is that tapping clones the application repository, and cask bumps are commits to `main`. A dedicated `bdchauvette/homebrew-tap` would allow `brew tap bdchauvette/tap`; it is not created, and the move is a file copy plus a token. The cask installs **the zip, not the dmg**: no volume to mount, and `app "beuve.app"` works directly. It sets `depends_on arch: :arm64` and `macos: :ventura` (ADR 0048's minimum), a `livecheck` on GitHub's latest release (which skips prereleases), and a `zap` for `~/Library/Application Support/beuve` (Electron's userData for this name) and the preferences, caches, logs and saved state for `dev.amoskeag.beuve`.
- **Gatekeeper.** Homebrew removed `--no-quarantine`, with no replacement, and refuses Gatekeeper-failing casks upstream. A custom tap may run its own code, so the cask has a `postflight_steps` step (the structured form; even `brew style` on a tap rejects the legacy `postflight` block) that runs `xattr -dr com.apple.quarantine` on its own installed app only, and says so in its caveats. Casks in a non-official tap need the user to trust it (`brew install --cask bdchauvette/beuve/beuve` trusts just that cask). Notarization (ADR 0048) would make the step unnecessary and it should be deleted then.
- **Keeping the cask current.** After the release is published, the workflow downloads the published zip, hashes it, checks the hash against `SHA256SUMS`, and pushes `chore(cask): beuve <version>` to `main` with `scripts/update-cask.ts`. It skips prereleases. A push made with `GITHUB_TOKEN` starts no workflow, and releases start only from tags, so it can't loop. A final macOS job installs the cask from the tap.
- **Cask checks.** CI on macOS taps the checkout and runs `brew style --cask` and `brew audit --cask --strict` (not `--online`, which would fail before a release exists).

## Consequences

Platform differences fail on every push instead of at release. A release is two commands, and the Homebrew install follows without a manual step; the cask's `sha256` is a placeholder until the first release bumps it, so install the cask only from a tag's commit or later. The quarantine removal is a deliberate weakening that applies to this one app and is stated in the caveats. If the release job's cask push is rejected (branch protection), the release is still published and the cask must be bumped by hand. Unlike GitHub's notes, ours credit no authors or pull requests.

## Amendment 2026-10-29: the cask leaves quarantine in place

The Gatekeeper bullet above is superseded. The cask no longer has a `postflight_steps` block and does not remove `com.apple.quarantine`. Clearing the flag is a trust decision about an unnotarized build, and the user makes it, not the package manager. The caveats say plainly that beuve is ad-hoc signed and not notarized, so the first launch is blocked, and give the two options: "Open Anyway" in System Settings > Privacy & Security after a blocked launch, or `xattr -dr com.apple.quarantine /Applications/beuve.app` by hand. Control-click > Open no longer bypasses Gatekeeper on macOS 15 and later. The `verify-cask` job now asserts that the install succeeded, the app bundle is present and its ad-hoc signature verifies; it does not launch the app.
