# 0162. Suggestions are a note's list of replacements, edited in CodeMirror fields and posted piece by piece

- Status: Accepted; supersedes [0043](0043-inline-edits-become-suggestions.md); amends [0035](0035-github-rest-client-scope.md) (refused comments), [0023](0023-universal-review-artifact-model-and-exporters.md) (suggestions, exports), [0039](0039-posting-reviews-and-posted-items.md) (placement, postings), [0068](0068-native-menus-chorded-keymap-and-a-settings-window.md) (Add Note's key) and [0088](0088-review-edits-branch-and-never-push.md) (harvest)
- Date: 2026-11-27

## Context

ADR 0043 made Add Suggestion… an editor attached to the file card: `@pierre/diffs/edit` on the hunk, an edit bar, the stream's keys held back while editing, and a refusal when an edit strays outside the target lines. It is modal state inside the component built for reading, and using it has not been pleasant. The model behind it is GitHub's: a note carries at most one `SuggestedPatch`, on the note's own path, changing only the note's own lines. GitHub can only post a suggestion on lines in the diff, and beuve took the limit on as its own: Turn into Suggestions (ADR 0088) drops change regions outside the lines the pull request changed, a rename that touches five files cannot be one note, and notes are only written from the diff stream. The JSON and XML exports, which go to agents and not to GitHub, inherit the same limits.

A review tool should be able to say "change this, and these four call sites" about any line at the head, and leave it to each export to carry that as well as its target allows.

## Decision

### The model

- **A note has a list of suggestions** in place of one patch: `UraItem.suggestions: readonly UraSuggestion[]`, each `{ path, startLine, endLine, replacement }`, on the head side of the item's `headSha`. Lines are 1-based and inclusive; `endLine = startLine - 1` is an insertion before `startLine` (after the last line when `startLine` is one past it). `replacement` is the text of the new lines, `\n`-joined, without a final newline; `''` is no lines, so a suggestion that leaves one empty line takes a neighboring line along, and an insertion adds at least one line.
- **Independent of the anchor.** A suggestion may be on any path of the head's tree, inside or outside the diff, and on lines the note's anchor does not cover. A whole-change or file note may carry suggestions. Paths follow the anchor rules (ADR 0023). Suggestions of one item never overlap; at most 500 per item and 64 KiB of replacement each (`validateUraItem`). Main checks each range against the head blob's line count before storing it, since the domain reads no files.
- **Patches are derived.** `suggestedPatchFrom` builds a unified diff for a suggestion at export, from the head blob, with three context lines, keeping `\r` and git's no-newline marker as `buildSuggestedPatch` did. Nothing stores a patch.
- **Re-anchoring per suggestion.** Each suggestion is re-anchored like a `lines` anchor (`reanchorUraAnchor`, GitHub's outdated rule); an insertion follows the line before it. An outdated suggestion is kept and carries its reason, in the notes list and in every export, so a rename is never silently missing one site.
- **Persistence.** Migration `ura-0004-suggestions` creates `ura_item_suggestions` (STRICT: `item_id` cascading from `ura_items`, `position`, `path`, `start_line`, `end_line`, `replacement`; primary key `(item_id, position)`; CHECKs for `start_line >= 1` and `end_line >= start_line - 1`) and converts every stored `suggested_patch`: each hunk becomes one suggestion over its old range, whose replacement is the hunk's new side. `ura_items` is then rebuilt without `patch` (ADR 0137's order): its CHECK that a note has a title, a body or a patch can't see the new table, so whether a note says something is the domain's to check.

### Writing suggestions

- **The inline editor goes.** Add Suggestion… no longer edits the card: `@pierre/diffs/edit`, the edit bar, `planEditTarget`, `editableDiffFrom`, `prepareForEditing`, the stream's editing state and the `editable-target` condition are removed. A card being edited no longer has to stay mounted.
- **Suggestion fields.** The note composer and the notes list's editor show a note's suggestions as fields, each headed by its `path:Lstart–end` and with Remove. A field opens pre-filled with the current text of its lines, so editing starts from the code.
  - **Add Suggestion…** (`add-suggestion`, ⌥⌘E / Ctrl+Shift+E, unchanged) on a line selection in the diff or a sheet adds a field for those lines: to the note being composed, else to a staged note under the cursor written against the head being shown, else to a new note on those lines.
  - The composer's **Add suggestion** button adds a field over the note's own lines; a note without lines takes the diff's current selection.
- **Fields are CodeMirror 6** (`@codemirror/state`, `@codemirror/view`, `@codemirror/commands`, exact versions pinned when added, no install scripts). No language packages: the field is highlighted with the tokens of beuve's own Shiki highlighter (ADR 0018, 0119), applied as mark decorations, so code in a field looks like code in the diff. The theme (`EditorView.theme`) uses only `--beuve-*` tokens and logical properties, and `local/css-design-tokens` checks it as it checks `css` templates. A spike (2026-11-27, Electron 45.3.4 / Chromium 156, the real default policy and the CSP as meta tag and header) found no CSP or Trusted Types violation, in the light DOM and in a shadow root: CodeMirror builds nodes, adds one `<style>` element under `document` (allowed by `style-src-elem 'unsafe-inline'`) and an adopted stylesheet under a shadow root, and decoration `style` attributes are allowed by `style-src-attr 'unsafe-inline'`. `@codemirror/commands` brings `@codemirror/language` and three `@lezer/*` packages for its indentation commands, so twelve packages arrive, all MIT and none with an install script; the setup above is about 263 KB minified (87 KB gzip). Transitive versions are pinned with `overrides` like the direct ones, to releases at least two weeks old. Fields are created with `root` set to the component's `renderRoot` (an editor built outside the shadow root and moved in keeps `document` as its root and gets no styles) and use `drawSelection()`, so the selection and caret take `--beuve-*` colors; the theme overrides every visible value of CodeMirror's base theme, whose literal colors and lengths are injected CSS that the lint never sees.
  - **Keys.** A minimal keymap: history (⌘Z / ⇧⌘Z), the platform's caret and selection keys, indent and outdent on ⌘] / ⌘[ (Ctrl+] / Ctrl+[), ⌘Return saves, Escape cancels. Tab moves focus, as everywhere else (ADR 0068). Nothing binds ⌘/ or ⌥↑/↓. A focused field reports `text-focus`, so menu chords marked `textConflict` (Back/Forward among them) are disabled while it has focus.
  - Each field has an accessible name ("Suggestion for src/retry.ts, lines 10 to 12").
- **Add Note is ⌘N / Ctrl+N** (was ⌘/ / Ctrl+/), the conventional "new item" key, leaving ⌘/ to its usual meaning in code fields.
- **Notes anywhere.** Add Note and Add Suggestion… work on lines outside the diff: unchanged lines the diff has expanded, and sheets (ADR 0067), whose menus gain both. A sheet does not write notes itself: it asks main (`sheet:add-note { headSha, path, startLine, endLine, suggest }`), and main has the main window open its composer on those lines, so notes keep one place where they are written.

### Turn into Suggestions (amends ADR 0088)

Every change region of the snapshot becomes a suggestion, whether or not the pull request changed those lines. A region attaches to the staged note at that head that covers it; the rest are grouped into one new note per file, labeled `suggestion` and anchored at its first region. The preview lists both.

### Posting to GitHub (amends ADR 0039)

Each piece of a note is placed on its own:

- **The note's comment** is inline on its anchor when GitHub can take it there (current, `lines`, inside `commentableRanges`). A suggestion covering exactly the note's lines goes in that comment as a condensed ` ```suggestion ` block, the replacement lines and nothing else.
- **Every other suggestion** inside `commentableRanges` is an inline comment of its own on its lines, with a ` ```suggestion ` block and a first line naming the note ("Suggestion 2 of 3 for **Rename `retries` to `retryBudget`**"; "Suggestion for …" when the note has one, and the label when it has no title). An insertion hangs on the line before it, which re-anchoring keeps unchanged, its block that line followed by the new ones; at the top of a file, on line 1 followed by nothing but only when the note was written against the head being posted, since nothing vouches for line 1 on a later one. Either line's text comes from the derived patch, so an insertion whose file couldn't be read has no line to hang on. A note the agent raised signs each of its comments and its section (ADR 0143).
- **Everything else goes in the review body, in `<details>`**: a note whose anchor GitHub cannot take, and every suggestion it cannot take (outside the diff, outdated, or an insertion with no line to hang on). One `<details>` per note, in note order, under the reviewer's summary: its `<summary>` is the note's headline (escaped with `escapeMarkdownHtml`), and inside are the note's text when it was not posted inline, then each suggestion as a ` ```diff ` block of its derived patch, with blank lines around every fence so GitHub renders Markdown inside the HTML block. This replaces "### Not attached to a line".
- **Permalinks for everything outside the diff.** Each line-anchored note and each suggestion placed in the body is preceded by a permalink to its lines (`permalinkFrom`, ADR 0067), on a line of its own, so GitHub shows the code beside it; a file note links to the file, an insertion to the line it follows. The link is to the head it is placed on: the current head, or for an outdated piece the head it was written against, labeled "(outdated)" by the line under it (`` `src/a.ts:3-5` (outdated: the lines changed since 1a2b3c4d5e6f) ``), since a link with text after it on its line is no longer shown as code. Links name the pull request's base repository, which serves a fork's commits too. `buildGithubReview` stays pure and in the `ura` domain: main passes `permalinkFor(target)`, built on `#internal/github/permalink-from.ts`, in its options, and without it (a local session's "Copy GitHub review") no links are written.
- **Size.** GitHub refuses a review body or comment over 65,536 characters (counted here in UTF-16 units, which never undercounts). When the body would exceed it, whole `<details>` blocks are left out from the end and a last line says how many ("_2 more notes and 12 more suggestions are in the exported review._"); nothing is cut inside a block or a fence. An inline comment that would exceed it moves to the body under the same rule: a note's comment that is too long puts the note's text in its section and leaves its condensed suggestion free to take a comment of its own. Pieces left out are not recorded as posted, and the preview counts them (`leftOutCount`).
- **Postings** record each place a note went (its comment, each separate suggestion comment, its body section). Migration `ura-0005-posting-pieces` rebuilds `ura_item_postings` with one row per piece: `piece` (`note`, the note's text, or `suggestion`) and the suggestion's `position` join the primary key, and `placement` is `comment` (the note's comment, which may carry a condensed suggestion), `suggestion-comment` or `body`. An existing row becomes the note's piece (`inline` is `comment`) plus a row per suggestion the note has, placed where the note went. A position doesn't name a suggestion for good, though: removing one hands its position to the next, and a suggestion added later could take a posted position and never be posted. So **suggestions have ids** (`UraSuggestionId`, a UUID from the injected `newId`, unique within the item): migration `ura-0006-suggestion-ids` rebuilds `ura_item_suggestions` with `id` (a random UUID for each existing row) and `ura_item_postings` with `suggestion_id` in place of `position` (`''` for the note's text), each suggestion posting taking the id now at its position and one whose position is empty dropped. An edit keeps a suggestion's identity when the client sends its id back (`UraSuggestionDraftView.id`, `uraSuggestionsFromDrafts`); a draft without one, or with an id the note doesn't have or an earlier draft already took, is a new suggestion with a fresh id, and a new note's suggestions are all new. A note counts as posted once its text and every suggestion it has now were (`isUraItemPosted`); a later post leaves out the pieces already posted, wherever they would go now, so a note posted inline that is outdated on the next head isn't posted again, and a suggestion added to a posted note is posted on its own (where ADR 0039 posted nothing for an edit). When GitHub refuses comments, main builds the review again with the pieces they carried in their notes' sections (`moveToBody`) and posts once more, so the postings say where each piece really went; the GitHub domain's own `move-to-body` fallback (`onRejectedComments`, `moveCommentsToBody`) is removed. The preview counts inline comments, body sections and notes posted whole.

### Exports (amends ADR 0023)

The agent JSON and XML follow none of GitHub's limits. They become `beuve.ura/2`: each item has `suggestions`, each with its path, its lines on the head the artifact is compiled for (or `outdated` with the reason and the lines it was written against), the replacement and the derived unified diff. In the XML, replacements and patches are CDATA with `]]>` split, as bodies are. A patch is derived from the head the note was written against, which for a re-anchored current suggestion is older than the artifact's head, so each patch names it (`against-sha`, `patchAgainstSha`). `beuve.ura/1` is no longer produced; the export is pasted, so there is no reader to keep.

## Consequences

The diff stream goes back to being read-only, and the largest piece of modal state in it goes. A note can say everything a reviewer means about the code, wherever it is, and each export carries as much as its target can: agents get all of it, GitHub gets inline suggestions where it allows and a readable, linked `<details>` section where it does not. CodeMirror is a real dependency (twelve packages, about 87 KB gzip) with its own focus and selection model, which the composer and the notes list's editor must host; using beuve's highlighter keeps one source of syntax styles at the cost of a small decoration plugin. Splitting one note into several GitHub comments scatters it on GitHub, which the "n of m for" line mitigates. Readers of `beuve.ura/1` must move to `/2`. Muscle memory for ⌘/ breaks once.

## Amendment 2026-11-27: the field as built

- **Versions.** `@codemirror/state` 6.7.6, `@codemirror/view` 6.43.15 and `@codemirror/commands` 6.11.1 are dependencies; `overrides` pins the nine packages they bring (`@codemirror/language` 6.13.1, `@codemirror/streamparser` 6.0.0, `@lezer/common` 1.5.5, `@lezer/highlight` 1.2.5, `@lezer/lr` 1.4.12, `@marijn/find-cluster-break` 1.0.4, `crelt` 1.0.7, `style-mod` 4.1.4, `w3c-keyname` 2.2.8), every one published by 2026-10-30, none with an install script, so `allowScripts` is unchanged. `npm audit` finds nothing new. esbuild bundles them into the renderer, so `electron-builder.yml` is unchanged.
- **A lazy chunk.** Only `create-suggestion-editor.ts` and `suggestion-editor-theme.ts` import `@codemirror/*` (dependency-cruiser `codemirror-only-in-suggestion-editor`), and `beuve-suggestion-field` imports the first with `import()`, so CodeMirror loads with the first field and the eager bundle stays as it was.
- **Highlighting.** A field's text is tokenized whole by `@pierre/diffs`' shared Shiki highlighter on the main thread, as diffs under 12 000 characters already are (ADR 0050), at most once a frame and not past 20 000 characters; a worker round trip per keystroke buys nothing at a suggestion's size. Tokens carry the library's `--diffs-token-light` / `--diffs-token-dark` properties as inline styles on mark decorations, and the theme picks the color with `light-dark()`, so a field follows `color-scheme` as the tokens do. Weight and slant are read from the light properties alone: the two themes give every class the same style (ADR 0119).
- **The lint reads the theme.** `local/css-design-tokens` and `local/css-logical-properties` check the object passed to `EditorView.theme` (or `baseTheme`) as they check a `css` template, its `camelCase` keys read as CSS properties.
- **Line endings.** A field over CRLF lines keeps them (`EditorState.lineSeparator`), so its replacement keeps the `\r` the derived patch expects.
- **A field outside the document** (a card's composer while the card is unmounted far from the viewport) tears its editor down and keeps its text, so the "card being edited stays mounted" rule has nothing left to protect; undo history does not survive that.
- **Where a field's text comes from.** A field without a replacement asks for its lines' text with a composed request event (`beuve-suggestion-lines`) that the review answers: from `session:get-file-pair` when the lines are on the head shown and the file is in the diff, else from `sheet:get-file` at the note's head, which reads any path of a session commit. A field whose lines can't be read starts empty and says so.
- **Add Suggestion… on a staged note** adds a field for the target's lines (the selection, else the focused hunk), not for the whole note: the note under the cursor is only where the field goes. A field that would overlap one the note has (as `validateUraItem` defines it) is not added; the existing one is focused, with a notice. A note written on an older head takes no lines from the diff, whose numbers are another file's; its own Add suggestion still works on its own lines at its head.
- **Add suggestion in the notes list's editor** takes the note's own lines; for a file or whole-change note it asks the review for the diff's selected lines (`beuve-suggestion-target`). Its "Edit suggestion…" and "Remove suggestion" buttons are gone: each field has Remove, and saving sends every field back with its id.
- **The menu condition** `editable-target` becomes `suggestion-target` (`unsuggestableReasonFrom`): only a deleted or binary file has no head lines. A file with no hunks is no longer excluded, since a field needs no changed line; the diff just offers none to select.

## Amendment 2026-11-27: Turn into Suggestions as built

- **Regions.** Each `--unified=0` hunk of a modified text file is one suggestion over its head lines, an insertion as a native insertion (`endLine = startLine - 1`), not a replacement of the line above. A region that leaves or inserts one empty line takes a neighboring line along, as the model requires. The harvest no longer reads the pull request's own diff: which lines it changed doesn't matter.
- **Attaching.** A region goes to a staged line note at the edits' base whose lines cover it (an insertion is covered by a note on the line before it, or on line 1 at the top), but only when the note has no suggestions or only ones an earlier harvest gave it, so a harvest never replaces suggestions the reviewer wrote; that note's regions join the file's new note instead. Each attached region is its own suggestion in the note's list; ADR 0088's merge of several regions into one patch over the note's lines is gone.
- **The file's note.** The other regions of a file form one note labeled `suggestion`, titled "Suggested changes to `path`", anchored at its first region (an insertion's at the line before it). Its harvest target is `suggestions:<path>`, and a note made this way never takes another file's regions or counts as a note to attach to. A staged note's target is `note:<id>`. A later harvest that changes either replaces its suggestions, reusing the id of a suggestion on the same lines so its postings stay.
- **Still notes with a diff.** A region that adds or removes the file's final newline, which a replacement can't say, and whole-file edits (new, deleted, renamed, copied, binary, submodule and mode-only files) stay notes with a ` ```diff ` block. The notes list's preview shows each item's suggestions under their `path:L` lines, with each derived patch, and each note's diff.
