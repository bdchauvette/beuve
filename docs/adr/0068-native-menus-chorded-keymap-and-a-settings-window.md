# 0068. Native menus from one command catalog, a chorded keymap, and a Settings window

- Status: Accepted (Settings holds only what no menu sets, amended 2026-11-06); amends [0044](0044-two-column-shell-open-flow-and-command-palette.md) (keys, Tab, status bar hints), [0064](0064-reviewed-marks-per-file-and-diff.md) and [0067](0067-sheets-definitions-and-permalinks.md) (their keys, sheets' menu bar), spec 5A
- Date: 2026-10-30

## Context

The review loop ran on bare letters (`j`/`k`, `v`, `m`, `e`, `o`, `p`, `r`, `s`, `w`, `f`, …), Tab cycled the zones, and the only list of keys was a `?` overlay and hint strips in the UI. beuve had no menu bar of its own (Electron's default), so macOS Help search and VoiceOver could not find a command, and sheets had no menu at all. Bare letters cannot be menu accelerators: on Linux a menu accelerator also fires while the reviewer types the letter in a field (checked below), they collide with VoiceOver Quick Nav and Orca's browse-mode letters, and taking Tab breaks Full Keyboard Access. Several preferences (editor, diff layout, whitespace, generated files, insights, order, sheets, sidebar side) were reachable only through chat commands. The approved proposal compared Kaleidoscope, Xcode, JetBrains, Meld, Zed, GitHub Desktop and the Apple and GNOME guidelines.

## Decision

- **One command catalog.** `src/contract/command-catalog.ts` lists every command once, as data: id, title, menu place (`menu`, `group`, `submenu`, `subgroup`; `linuxMenu` where Linux differs), Electron accelerators per platform (`mac`, `linux`, and hidden alternates), in-place keys for the shortcuts window, context-menu kinds, enablement conditions (`when`), `textConflict`, `toggle` (checkbox or radio), the window kinds it runs in and whether main or the window handles it. Main builds every menu from it; `src/ui/command-registry.ts` adds only what each id does in the main window (an app action, a zone's `runCommand`, a chat command, or `menu:run-main`) plus `/help` text, and its test fails unless both list the same ids. **Every command is in the catalog, and every shortcut has a menu item** (a test on both platforms).
- **No bare-letter keys, no vim preset.** Every chorded key is a menu accelerator; in-place keys keep their usual control meaning (arrows, Return, Space, Delete, Home/End, Esc, ⌥↑/⌥↓ to move a note in the review list). The top bindings (macOS / Linux): Next and Previous Change ⌘↓ ⌘↑ / Alt+↓ Alt+↑ (F7, ⇧F7 too), Next and Previous File ⌥⌘↓ ⌥⌘↑ / Ctrl+PgDn Ctrl+PgUp, File Reviewed ⌘D / Ctrl+D (a toggle; it never advances), Save Progress ⌘S / Ctrl+S, Add Note ⌘/ / Ctrl+/, Add to Chat ⌘> / Ctrl+>, Show Callers ⌘I / Ctrl+I, Show Control Flow ⇧⌘I / Ctrl+Shift+I, Go to Definition ⌘B / Ctrl+B (F12), Type Definition ⇧⌘B / Ctrl+Shift+B, Open in Editor ⌥⌘O / Ctrl+Shift+O, Run Trace Probe ⌘R / Ctrl+R, Suggest Edit ⌥⌘E / Ctrl+Shift+E, ImpactGate Details ⌥⌘I / Alt+Return, Copy GitHub Permalink ⇧⌘C / Ctrl+Shift+C, Focus Chat ⌘L / Ctrl+L, Find ⌘F, Find Next/Previous ⌘G ⇧⌘G, Match Case ⌥⌘C (it typed `ç` as Alt+C on macOS), Command Palette ⌘K (⇧⌘P), Go to File ⌘P, Open ⌘O, Settings ⌘, / Ctrl+,, Sidebar ⌃⌘S / F9 and ⌘1–3, Back/Forward ⌘[ ⌘] / Alt+← Alt+→, Expand/Collapse File ⌥⌘→ ⌥⌘← / Ctrl+Shift+] [, Next/Previous Region ⌃Tab ⌃⇧Tab / F6 Shift+F6, Stop ⌘. (none on Linux, where Ctrl+. is the IBus emoji picker). Low-frequency preferences are menu items without keys. Tests reject duplicate accelerators per platform, bare keys, the reserved macOS chords (⌘Q ⌘W ⌘H ⌥⌘H ⌘M ⌘Space ⌘Tab, ⌘ plus backtick, ⇧⌘3/4/5 ⌃⌘Q ⌥⌘Esc ⌥⌘D ⇧⌘/) and on Linux Super chords, Ctrl+Alt+arrows, Ctrl+. and Alt plus a top-level menu's access key.
- **Menus.** macOS: the app menu (About, Settings…, Services, Hide, Quit) and File, Edit, View, Go, Review, Chat, Window (the `windowMenu` role) and Help (the `help` role, so Help search covers every command). Linux: the same without the app menu (About in Help, Preferences… in Edit, Quit in File), with `&` access keys unique per menu. Edit always has the Undo/Cut/Copy/Paste/Select All roles: macOS text fields need them. Secondary keys are hidden items, which work on both platforms. Development builds add Toggle Developer Tools (⌥⌘J / Ctrl+Shift+J). `menuTemplateFrom` and `contextMenuTemplateFrom` are pure and snapshot-tested per platform.
- **The menu is the single dispatcher of chords.** A click or accelerator sends `menu:run { id }` to the window it came from, and only for a command that window's kind runs and its last state enables; `main` commands (Settings, About, Close All Sheets, beuve on GitHub) run in main. The renderer has no handler for a chord any more (`handleModifiedKey`, the zone letter handlers, the palette's synthetic keydown are gone); zones expose `runCommand(id)`. Each window reports `menu:set-state { conditions, checked }` (validated: known conditions and ids only); main sets `enabled` and `checked` in place. macOS shares one app menu, which takes the focused window's state on focus; Linux gives every window its own menu.
- **Text fields keep their keys.** While a text field has focus the window reports `text-focus`, and main disables every `textConflict` item (⌘↑/↓, ⌥⌘arrows, ⌘[ ⌘], ⌘I, Ctrl+PgUp/PgDn, Ctrl+Shift+[ ]). Spike on Linux (Electron 45, X11, real key events through xdotool): the page sees every chord first; an editing key the field consumes (Ctrl+↓ in a textarea) never reaches the menu even when the item is enabled; a chord the field does not consume (Alt+↓, Ctrl+D, Ctrl+K, Ctrl+>) fires the enabled item and leaves the field alone; a disabled item lets its key through untouched; a bare-letter accelerator (`J`) fired _and_ typed the letter, which is why bare letters are out. **Not verified from this container (macOS):** Chromium on macOS also offers key equivalents to the page before the menu, and Cocoa editing keys (⌘↓, ⌥⌘→) are executed as editing commands, so the design does not rely on ordering: the items are disabled while a field has focus. If a macOS build ever shows a chord reaching the menu while typing, `webContents.on('before-input-event')` is the fallback.
- **Regions and Tab.** Tab and Shift+Tab move focus normally again (the chat input no longer captures them). Next/Previous Region (⌃Tab/F6) cycles diff, files, review notes and chat.
- **Context menus** come from the same catalog: diff line or selection, file header, tree row, review note, chat answer (Stage Answer as a Note), sheet, and the editing roles in text fields. The renderer asks with `menu:context { kind, x, y }` after pointing the target at what was clicked; accelerators are shown but not registered.
- **Sheets get menus.** On Linux a sheet has the menu bar hidden until Alt (`autoHideMenuBar`); on macOS the app menu follows the focused sheet. The sheet preload adds `onMenuRun` and the sheet channels add `menu:set-state` and `menu:context`. A sheet runs Back, Forward, Find, Find Next/Previous, Next/Previous Change (its change marks), Go to Definition, Type Definition, Copy GitHub Permalink and Open on GitHub. Its own keys are ↑/↓, Home/End and Esc.
- **No key hints in the UI.** The status bar names the region only; the `? keys`, the titlebar's ⌘K, "with neighbours · f", "Space on the card", the dock's key strip and editor hints, the composer, find bar, open panel, palette, portal and sheet hint strips are gone. Shortcuts show in menus, context menus, the palette's key column, tooltips ("Command Palette (⌘K)", "Reviewed — click to unmark (⌘D)", "Expand File (⌥⌘→)", "Close (Esc)") and Help ▸ Keyboard Shortcuts, which is generated from the catalog and grouped by menu, then by in-place area. The tree's header row has a proper **All · Changed** toggle mirroring View ▸ Changed Files Only.
- **Save Progress.** The header's "Mark reviewed" (the checkpoint of ADR 0009, 0012: the reviewed base and head, so the next visit shows an interdiff) is now **Save Progress** (⌘S, Review ▸ Save Progress). After saving, the header says "Progress saved · <sha7> · <time>" with the tooltip "Next time, show only what changed since this point". "Checkpoint" stays the internal term.
- **Settings window** (⌘, / Ctrl+,; Preferences on Linux): one small fixed-size window with the ADR 0005 baseline, `src/ui/settings.html` under the same CSP, and its own preload exposing only `settingsInvokeChannels` (`display:get`/`set`, `editor:get-settings`/`set-preferred`, `github:auth-status`, `claude:status`, `trace:list-trust`, `trace:remove-trust`, `menu:set-state`), enforced again per page in main. It holds the preferred editor, review order, skipping reviewed files, where definitions open, diff layout, whitespace, generated files, insights and sidebar side, an **Accounts** section (read-only), and the trusted repositories, each removable. A successful change from any window sends `settings:changed` to the others, which read the preferences again. The chat commands stay as shortcuts.
- **Accounts.** GitHub shows the gh login and host, or the signed-out hint ("run gh auth login"), from `github:auth-status`. Claude shows the CLI the chat would run and the first line of `claude --version` (`claude:status`, three-second limit); there is no cheap login check without a model call, so none is made. Each provider is one row, laid out so a write-only key field can be added. **API keys**, once main wires a consumer (the Agent SDK adapter of [0069](0069-agent-sdk-adapter-with-an-api-key.md), a GitHub token provider), will be stored by main with Electron `safeStorage` (Keychain on macOS, libsecret on Linux), entered write-only in this window, never written to `settings.json` and never sent back to a renderer. No key storage is built yet.

## Consequences

Every command is discoverable in a menu and searchable on macOS, and keys cannot drift between the menu, the palette, tooltips and the shortcuts window. Reviewers used to single letters relearn chords; there is no preset to keep them. The renderer must report its state for enablement, so a command's `when` and the window's conditions must agree (table tests cover `menuStateFrom` and `menuItemStatesFrom`). Adding a command means a catalog entry and a registry behaviour; a shortcut without a menu item fails a test. The Settings window adds a page, a preload and three channels (`claude:status`, `trace:list-trust`, `trace:remove-trust`) to the security surface; adding a channel to it means adding it to `settingsInvokeChannels` deliberately. Open Recent, the Linux Window menu's list of sheets and main-window Back/Forward history are not built.

## Amendment 2026-10-30: Models and key storage

ADR 0070 adds Settings ▸ Models and builds the key storage described above: `<userData>/model-secrets.json` holds `safeStorage` ciphertext, keys are entered write-only, and the `models:*` channels are the Settings window's alone (`settingsOnlyInvokeChannels`; the main window is registered with `mainWindowInvokeChannels` instead of every channel). The window is 620 by 780 points.

## Amendment 2026-11-03: sidebar tab keys (ADR 0109)

The sidebar has four tabs for a pull request: ⌘1 Overview, ⌘2 Files, ⌘3 Review, ⌘4 Chat (Ctrl+1 to Ctrl+4 on Linux and Windows). ⌘1 is enabled only for a pull request.

## Amendment 2026-11-06: Settings holds only what no menu sets

A preference with a menu toggle is set from the menu, and only there: diff layout, whitespace, generated files, insights, diagnostics, review order, skipping reviewed files, sidebar side and the preferred editor (Review › Open With) leave the Settings window. The menu items, their chat commands and `settings.json` keep them; Settings showed the same state a second time and had to be kept in step with the menus. Settings now holds the review-edits and review-queue branch prefixes (Branches), the accounts, the language server configuration and the models. `display:set` and `editor:set-preferred` stay on the Settings window's channels, the first for the queue prefixes. A new preference that gets a menu toggle does not get a Settings row, and one without a menu item may.
