# 0048. Packaging, signing and release with electron-builder

- Status: Accepted (fuses and the Node launch path amended by [0083](0083-run-as-node-fuse-off-and-a-bundled-node.md))
- Date: 2026-10-29

## Context

beuve targets macOS (spec header) but had no way to become an app: `npm start` runs Electron against `dist/`. beuve is for personal use for now, with no Apple Developer ID, and runs on Apple silicon. A release needs an arm64 app as a dmg and a zip that the author can run on their own Mac. Developer ID signing with the hardened runtime and notarization have to stay possible from environment credentials for later. It also needs an asar archive that leaves out what tsserver can't read from inside one, and a Linux build so packaging can be smoke-tested in a Linux container. Main loads a few things by path at run time, and those paths have to keep working packaged: the Tree-sitter wasm (ADR 0014), the preload and `index.html` (ADR 0005, 0011), and `typescript-language-server` and `tsserver`, which run as `process.execPath` with `ELECTRON_RUN_AS_NODE=1` (ADR 0017, 0021). Trace probes run Vitest the same way (ADR 0036). Two environment variables exist only to drive an unpackaged app against fakes (ADR 0033, 0040).

The options:

- **Electron Forge** is the Electron project's default, but it is a CLI plus a plugin and maker per concern (`@electron-forge/cli`, `maker-dmg`, `maker-zip`, the fuses plugin, a universal option), about a dozen packages. Its dmg maker uses `appdmg`, which builds only on macOS, and it has no AppImage maker.
- **@electron/packager** with `@electron/osx-sign`, `@electron/notarize` and `@electron/universal` is the lowest layer. We would write the dmg, zip, fuses and AppImage glue ourselves.
- **electron-builder** is one devDependency with one declarative config file. It covers dmg and zip for any macOS architecture, hardened runtime and entitlements, notarytool notarization from `APPLE_*` variables, asar with `asarUnpack`, fuses, and Linux `dir` and AppImage. Internally it uses the same `@electron/osx-sign`, `@electron/notarize` and `@electron/asar`.

## Decision

- **Packager: `electron-builder@26.17.0`**, pinned exactly as a devDependency (released 2026-09-26; 26.18 was nine days old). Its install tree is large (about 90 MB in `node_modules`), but it is dev-only, nothing of it ships, and the alternatives cost as many packages for less coverage. Config lives in `electron-builder.yml`; output goes to `out/`, because `dist/` is esbuild's.
- **What ships.** `dist/**` without source maps, `package.json`, and from `node_modules` only what main launches by path: `typescript` (`lib/*.js` except `tsc`, `lib/lib.*.d.ts`, `typesMap.json`, `package.json`, licence) and `typescript-language-server` (`lib/cli.mjs`, `package.json`, licence). Every other runtime dependency is inside the esbuild bundles (ADR 0007), so lit, zod, the MCP SDK and the Pierre libraries are excluded rather than copied twice. The two packages use `from`/`to` file sets because electron-builder drops every `*.d.ts` it collects from `node_modules`. Nothing is native (ADR 0004), so `npmRebuild` is off. Sizes measured on Linux x64: `app.asar` 8.3 MiB (wasm 3.3 MiB, ui chunks 2.5 MiB, main bundle 2.2 MiB), `app.asar.unpacked` 13.3 MiB (almost all TypeScript: `typescript.js` 8.7 MiB, `lib.dom.d.ts` 2.2 MiB), the app directory 295 MiB (the Electron binary is 224 MiB), and the AppImage 123.7 MiB.
- **Unpacked: `typescript` and `typescript-language-server`**, and main launches them from `app.asar.unpacked` (`toUnpackedPath` in `create-typescript-server.ts`). Electron's asar support does reach `ELECTRON_RUN_AS_NODE` children: both start from inside the archive and answer call hierarchy. But tsserver then resolves its `lib.*.d.ts` only partly and reports wrong diagnostics (`Property 'length' does not exist on type '{}'` on a `readonly number[]`), with no error anywhere. From the unpacked directory it reports none, as plain Node does. The wasm, preload, `index.html` and ui chunks are read by Electron's own loaders and stay in the archive.
- **Fuses.** `runAsNode` stays on, because language servers and trace probes need it. `enableNodeOptionsEnvironmentVariable` and `enableNodeCliInspectArguments` are off, so `NODE_OPTIONS` and `--inspect` can't be used to inject code into the signed binary. Cookie encryption is on. On macOS, `onlyLoadAppFromAsar` and `enableEmbeddedAsarIntegrityValidation` make the app load only the signed `app.asar` whose hash is in `Info.plist`. Trace probes and the language server were checked to work with these fuses. The cost: anything running as the user can run `beuve.app` as a Node interpreter under beuve's code signature and its TCC grants, which beuve has none of beyond what any app gets.
- **macOS.** `appId` `dev.amoskeag.beuve`, `productName` `beuve`, category `public.app-category.developer-tools`, `minimumSystemVersion` 13.0 (Electron 44 and later require macOS 13). **Apple silicon only**: an arm64 dmg and zip, no x64 or universal build, which keeps the download at one architecture's size and drops the universal merge step. An Intel build is one `arch` entry in `electron-builder.yml` away. Developer ID builds use the hardened runtime with a single entitlement for the app and its helpers, `com.apple.security.cs.allow-jit`, which V8 needs. That is the only entitlement in `@electron/osx-sign`'s own default besides device access. We don't need `allow-unsigned-executable-memory`, which that default dropped (V8 uses `MAP_JIT` under `allow-jit`), or `disable-library-validation` (every library is in the bundle and signed with our team ID). There are no `Info.plist` usage strings: the folder picker is an `NSOpenPanel`, which needs none outside the sandbox, and beuve uses no camera, microphone, location or Apple Events.
- **Not the Mac App Store, no app sandbox.** beuve spawns `git`, `gh`, `claude`, the reviewer's editor, language servers and the repository's own Vitest, reads repositories wherever they are, and writes worktrees under `userData`. The App Sandbox forbids running the user's executables and reading outside granted folders, so beuve is distributed directly with Developer ID and notarization.
- **Signing model: ad-hoc by default, for personal use** (`scripts/dist-mac.ts`, `npm run dist:mac`). There is no Developer ID today, so the normal build is ad-hoc signed and runs on the author's Mac after a Gatekeeper override (Control-click › Open, or `xattr -dr com.apple.quarantine`; docs/packaging.md). The signed path stays available without code changes: with `CSC_LINK` (a base64 or path `.p12` of the "Developer ID Application" certificate, plus `CSC_KEY_PASSWORD`) or `CSC_NAME` (an identity already in the keychain), the build signs with the hardened runtime, and `forceCodeSigning` turns a missing identity into an error. It notarizes when a complete credential set is present, in electron-builder's order: `APPLE_ID`, `APPLE_APP_SPECIFIC_PASSWORD` and `APPLE_TEAM_ID`; or `APPLE_API_KEY` (path to the `.p8`), `APPLE_API_KEY_ID` and `APPLE_API_ISSUER`; or `APPLE_KEYCHAIN_PROFILE`. electron-builder then staples the ticket to the app. Without a certificate, which is the default, the script builds ad-hoc signed (`identity: '-'`, required on Apple silicon) without the hardened runtime and says so. Library validation would reject ad-hoc signed frameworks, and adding `disable-library-validation` to make it pass would weaken signed builds too. The script refuses to run off macOS. `npm run dist:linux-dir` and `npm run dist:linux` (AppImage) are unsigned.
- **Development overrides are inert when packaged.** `readDevelopmentOverrides(app.isPackaged, env)` is the only reader of `BEUVE_GITHUB_API_URL` and `BEUVE_EDITOR_LAUNCH_LOG`. It returns nothing when packaged, and main logs the variables it ignored. It is unit-tested and was checked in the packaged app. `BEUVE_CLAUDE_PATH`, `BEUVE_GH_PATH`, `BEUVE_MCP_PORT` and `BEUVE_LOG_LEVEL` are user settings (they name the user's own executables, port and verbosity), not fakes, and keep working packaged.
- **Icon.** `scripts/build-icon.ts` draws the placeholder icon analytically (signed distance fields at each size; a lowercase "b" and an insight dot in the Alabaster palette on Apple's 1024 grid). It writes `build/icon.icns` and `build/icon.png` through `#pkg/image/encode-png.ts` and `encode-icns.ts`, which use `node:zlib` only, so no rasterizer, `iconutil` or image dependency is needed. The outputs are committed.
- **CI.** `.github/workflows/ci.yml` runs `npm run check` on Ubuntu for pushes and pull requests. `.github/workflows/release.yml` runs on `macos-latest` (Apple silicon runners) for `v*` tags and manual dispatch: `npm ci`, `npm run check`, then `npm run dist:mac` **with no secrets**, so it always produces the ad-hoc build. Then it uploads the dmg and zip as an artifact and, for a tag, creates a draft GitHub Release with `gh`. Node 24 matches Electron 45's. Actions are pinned to major versions (`actions/checkout@v4`, `actions/setup-node@v4`, `actions/upload-artifact@v4`).

## Consequences

One config file and one dev dependency cover both platforms, and the Linux directory build is a faithful stand-in for the macOS app's contents, so it can be smoke-tested in a container. The macOS build and the asar integrity fuse run only on macOS. They are exercised by the release workflow, not in the Linux container. Developer ID signing and notarization are configured but have never run. Turning them on means adding the secrets and passing them to the workflow's `dist:mac` step. Intel Macs are not supported. An upgrade of TypeScript or `typescript-language-server` must keep the file lists in `electron-builder.yml` in step: a missing file surfaces only in the packaged app. Unpacked TypeScript is covered by the bundle's code signature but not by the asar integrity check. Ad-hoc builds are for the author's own Mac. On other Macs Gatekeeper blocks them unless each user overrides it, so sharing beuve with others needs the Developer ID path (docs/packaging.md). Auto-update, a Windows build and a signed dmg are not part of this decision.
